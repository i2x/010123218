กลับไปหน้าสารบัญ

ช่วงที่ 5 แนวข้อสอบและการออกแบบ Architecture

สรุปจากแนวข้อสอบที่ได้รับมา และใช้โปรเจกต์ "คันนี้ดีไหม?" (github.com/i2x/bus) ที่ทีมเคยออกแบบและ deploy จริง เป็นตัวอย่างฝึกตอบโจทย์ออกแบบ

ช่วงนี้ต้องเข้าใจอะไร

ข้อสอบมี 4 ข้อใหญ่ ข้อ 1 กับ 2 ถามความรู้พื้นฐานจากสไลด์ช่วงต้นถึงกลางเทอม ส่วนข้อ 3 กับ 4 รวมกันเป็นคำถามใหญ่ข้อเดียว ให้ออกแบบระบบของโปรเจกต์แบบ 2 tier (แบ่งระบบเป็นสองชั้น) ตามที่อาจารย์กำหนด แล้วกำหนด instance (เครื่องเสมือนหรือ VM หนึ่งเครื่องบน Cloud) และตั้งค่า Cloud

ช่วงนี้จึงมีสองหน้าที่ หน้าที่แรกคือบอกว่าข้อ 1–2 ต้องกลับไปอ่านหัวข้อไหน หน้าที่ที่สองคือฝึกข้อ 3–4 เราจะไล่ดูว่าโปรเจกต์ของเราตัดสินใจอะไรไปบ้างและเพราะอะไร แล้วขยายแบบนั้นให้ทนต่อการล่มได้ในระดับที่โจทย์ข้อสอบมักขอ สิ่งที่อยากให้ติดตัวออกไปคือลำดับการคิดที่ใช้ได้กับทุกโจทย์ ไม่ใช่จำแบบของโปรเจกต์นี้ไปแบบเดียว

1. ข้อสอบมีหน้าตาแบบไหน

ข้อสอบจริงเป็นข้อเขียน ไม่ใช่ปรนัยแบบใน ข้อสอบจำลอง ข้อสอบจำลองยังใช้เช็กได้ดีว่าเข้าใจเนื้อหาหรือยัง แต่ตอนสอบจริงเราต้องเขียนอธิบายเอง หัวใจของการเขียนให้ได้คะแนนคือตอบสามขั้นในทุกข้อย่อย ขั้นแรกบอกว่าสิ่งนั้นคืออะไร ขั้นที่สองบอกว่าทำไมต้องมี หรือทำงานอย่างไร ขั้นสุดท้ายยกตัวอย่างหนึ่งอย่าง ถ้าโจทย์ให้เปรียบเทียบ ให้ตั้งเกณฑ์ก่อน แล้วเทียบทีละเกณฑ์ เช่น เทียบ public subnet กับ private subnet (วงเครือข่ายย่อยที่หันออกอินเทอร์เน็ต กับวงที่ซ่อนไว้ข้างใน) ด้วยสามเกณฑ์ คือมี route ไป Internet Gateway (ประตูออกอินเทอร์เน็ต) ไหม เครื่องมี public IP ไหม และวางอะไรไว้ข้างใน

ข้อ 1 และ 2 ถามความรู้พื้นฐาน ตัวอย่างโจทย์ที่ได้รับมาคือคุณสมบัติของ Cloud และ public/private subnet ทั้งสองเรื่องมาจากสไลด์ช่วงต้นถึงกลางเทอม ตรงกับช่วงที่ 1 และช่วงที่ 2 ของสรุปนี้ หัวข้อที่ควรอ่านให้แม่นที่สุดมีดังนี้

เรื่องอ่านที่ต้องตอบได้
นิยาม Cloud และลักษณะ 5 ข้อตาม NISTช่วง 1 ข้อ 5, ข้อ 6บอกครบทั้ง 5 ข้อพร้อมตัวอย่างของแต่ละข้อ
IaaS, PaaS, SaaS และแบบ public/private/hybrid cloudช่วง 1 ข้อ 7, ข้อ 8ใครดูแลชั้นไหน และยกตัวอย่างบริการของแต่ละแบบ
Region และ Availability Zoneช่วง 1 ข้อ 9ทำไมต้องกระจายเครื่องไว้หลาย AZ
Private IP, public IP และ NATช่วง 1 ข้อ 4ทำไมเครื่องที่มีแต่ private IP ยังออกเน็ตได้
Virtualization, hypervisor, containerช่วง 1 ข้อ 10, ข้อ 17Type 1 กับ Type 2 และ VM กับ container ต่างกันยังไง
VPC, CIDR และ public/private subnetช่วง 2 ข้อ 1 ถึง ข้อ 4คำนวณจำนวน IP และบอกว่าอะไรทำให้ subnet เป็น public
Route table, Internet Gateway, NAT Gatewayช่วง 2 ข้อ 5, ข้อ 6เขียน route table ของทั้งสอง subnet ได้
สถาปัตยกรรมแบบ tierช่วง 2 ข้อ 9แต่ละ tier วางไว้ที่ไหน และขยายแบบไหน

ถ้าเวลาเหลือ ให้อ่านช่วงที่ 3 ต่อ เรื่อง Security Group กับ NACL (ด่านกรอง traffic ระดับเครื่องและระดับ subnet) และ IAM (การกำหนดสิทธิ์ว่าใครทำอะไรได้) เพราะข้อ 3–4 ต้องใช้แน่นอน

ข้อ 3 และ 4 ใช้โจทย์เดียวกัน โจทย์จะเล่าความต้องการของระบบหนึ่งระบบ แล้วให้ออกแบบ architecture (โครงสร้างของระบบ) กำหนด instance และตั้งค่า Cloud ตอนนี้ยังไม่รู้แน่ว่าสองข้อนี้แบ่งเนื้อหากันอย่างไร แต่น่าจะเป็นข้อหนึ่งให้วาดและอธิบายโครงสร้าง อีกข้อให้ลงรายละเอียด instance และการตั้งค่า จึงควรเตรียมทั้งสองส่วน หัวข้อที่เหลือของช่วงนี้จะใช้โปรเจกต์ของเราเป็นตัวอย่างฝึกโจทย์แบบนี้

2. โจทย์ออกแบบต้องตอบอะไรบ้าง

หัวใจของโจทย์ออกแบบคือเหตุผล โจทย์แบบนี้ไม่มีคำตอบเดียวที่ถูก ผู้ตรวจดูว่าเราเลือกแต่ละอย่างด้วยเหตุผลที่ตรงกับความต้องการในโจทย์หรือเปล่า จึงควรตอบตามลำดับเดียวกันทุกครั้ง ลำดับนี้เรียงให้การตัดสินใจขั้นหลังต่อยอดจากขั้นก่อนหน้า

ขั้นแรกคืออ่านโจทย์หาความต้องการ ให้ขีดเส้นใต้สี่เรื่อง เรื่องแรกคือผู้ใช้มากน้อยแค่ไหน และเข้ามาเป็นช่วง ๆ หรือเปล่า เรื่องที่สองคือระบบล่มได้ไหม เรื่องที่สามคือข้อมูลอ่อนไหวแค่ไหน เรื่องสุดท้ายคือมีข้อจำกัดเรื่องงบ หรือมีเครือข่ายเดิมของบริษัทที่ต้องต่อด้วยไหม แต่ละเรื่องจะไปกำหนดการตัดสินใจในขั้นหลัง เช่น "ห้ามล่ม" แปลว่าต้องใช้อย่างน้อยสอง AZ (Availability Zone) AZ คือกลุ่ม data center ใน Region เดียวกันที่แยกไฟและเครือข่ายออกจากกัน ส่วน "คนเข้าพร้อมกันเป็นช่วง" แปลว่าต้องมี Auto Scaling คือระบบที่เพิ่มหรือลดจำนวนเครื่องให้เองตามปริมาณงาน

ขั้นที่สองคือแบ่งระบบเป็น tier ระบบเว็บเกือบทุกระบบแบ่งได้เป็นสามชั้น คือชั้นหน้าบ้าน (presentation) ชั้นตรรกะของแอป (application) และชั้นข้อมูล (data)

ขั้นที่สามคือวางเครือข่าย เริ่มจากเลือกช่วง IP ของ VPC (Virtual Private Cloud) ซึ่งคือเครือข่ายส่วนตัวที่เราแบ่งไว้บน Cloud ช่วง IP นี้เขียนแบบ CIDR คือเลขที่อยู่ตามด้วยจำนวนบิตที่ล็อกไว้ เช่น 10.0.0.0/16 หัวใจของ CIDR คือขนาด เลขหลังขีดบอกว่าวงนี้จุที่อยู่ได้กี่ตัว จากนั้นแบ่ง subnet (วงย่อยใน VPC) ตาม tier และตาม AZ แล้วเขียน route table (ตารางเส้นทาง) ว่า subnet ไหนออกเน็ตทางไหน

ขั้นที่สี่คือกำหนด instance (VM หนึ่งเครื่องบน Cloud) ว่าแต่ละ tier ใช้กี่เครื่อง ขนาดเท่าไร อยู่ subnet ไหน และมี public IP หรือไม่ ขั้นที่ห้าคือตั้งค่าความปลอดภัย ซึ่งมีเครื่องมือสามอย่าง Security Group (SG) เป็นด่านกรอง traffic ระดับเครื่อง NACL (Network Access Control List) เป็นด่านกรองระดับ subnet และ IAM (Identity and Access Management) เป็นระบบกำหนดว่าใครทำอะไรกับทรัพยากรไหนได้ ขั้นสุดท้ายคือทำให้ระบบทนและดูแลได้ ได้แก่ การกระจายเครื่องไปหลาย AZ การขยายจำนวนเครื่อง การ backup และช่องทางที่ผู้ดูแลใช้เข้าไปจัดการเครื่อง

คำตอบที่ดีมีทั้งภาพและตาราง ภาพบอกว่าของแต่ละชิ้นอยู่ตรงไหน และ traffic (ข้อมูลที่วิ่งในเครือข่าย) วิ่งทางไหน ตารางบอกค่าที่ตั้ง ควรมีอย่างน้อยสามตาราง คือตาราง subnet ตาราง instance และตารางกฎ SG ทุกตารางควรมีคอลัมน์ "เหตุผล" เพราะเป็นส่วนที่ผู้ตรวจให้คะแนน

3. โปรเจกต์ "คันนี้ดีไหม?" ทำอะไร

โปรเจกต์ของทีมเป็นเว็บสำหรับค้นหาและรีวิวรถเมล์ ขสมก. ทีละคัน ผู้ใช้กรอกหมายเลขข้างรถ เช่น 7-3077 แล้วจะเห็นรุ่นรถ เขตการเดินรถ ค่าโดยสาร และคะแนนจากผู้โดยสารสามด้าน คือการขับ การจอดป้าย และสภาพรถ คนที่เขียนรีวิวจะได้แต้มไปแลกสติกเกอร์ ถ้ารีวิวไหนถูกรายงานครบสามคน รีวิวนั้นจะถูกซ่อน แล้วให้ผู้ใช้ห้าคนที่สุ่มมาโหวตตัดสิน

แต่ข้อสอบไม่ได้ถามเรื่องฟีเจอร์ สิ่งที่ต้องดูคือระบบนี้มีโปรแกรมสามตัว ตัวแรกคือหน้าเว็บ เป็นไฟล์ HTML, CSS และ JavaScript ที่ไม่เปลี่ยนไปตามผู้ใช้ เรียกว่า static ไฟล์พวกนี้ส่งให้ผู้ใช้ด้วย Nginx ซึ่งเป็นโปรแกรม web server ตัวที่สองคือ REST API คือช่องทางที่หน้าเว็บใช้ขอข้อมูลผ่าน HTTP โดยระบุ URL และ method เช่น GET /api/buses/7-3077 ตัวนี้เขียนด้วย Node.js รันที่ port 3000 และเป็นที่เก็บกฎทั้งหมดของระบบ เช่น การคิดแต้มและการตรวจสิทธิ์ ตัวที่สามคือฐานข้อมูล PostgreSQL ที่ port 5432 ใช้เก็บข้อมูลผู้ใช้ รีวิว และประวัติแต้ม

อาจารย์กำหนดให้โปรเจกต์ใช้สถาปัตยกรรมแบบ 2 tier โปรแกรมสามตัวจึงต้องจัดลงในสองชั้น นิยามในสไลด์ Week 3 คือแยกฐานข้อมูลออกจากเครื่องที่รันเว็บและแอป ชั้นแรกจึงเป็น web + app server ที่มี Nginx กับ API อยู่เครื่องเดียวกัน ส่วนชั้นที่สองเป็น database server สามโปรแกรมนี้ยังตรงกับสามแล็บที่เคยทำ หน้าเว็บกับ Nginx ตรงกับแล็บ GetStart การแยกหน้าเว็บ API และฐานข้อมูลออกจากกันตรงกับแล็บ WebApp และการกั้นว่าใครคุยกับใครได้ตรงกับแล็บ Build VPC

4. แบบ 2 tier ที่ใช้ตอบข้อสอบ

หัวใจของ 2 tier คือเอาฐานข้อมูลออกไปไว้ในที่ที่คนข้างนอกเข้าไม่ถึง ส่วนเว็บกับแอปยังอยู่ด้วยกัน ถ้าวางบน AWS (Amazon Web Services) แบบนี้ใช้ VPC 10.0.0.0/16 หนึ่งวง subnet สองวง และ EC2 (Elastic Compute Cloud บริการเช่า VM ของ AWS) สองเครื่อง แบบนี้เป็นคำตอบของโจทย์ออกแบบขนาดเล็กที่มีองค์ประกอบครบ ควรจำให้ได้เป็นภาพ

Public subnet 10.0.1.0/24 มี route ที่ส่ง traffic ปลายทาง 0.0.0.0/0 (ทุกที่ที่ไม่ได้อยู่ในวง) ไปที่ IGW (Internet Gateway) ซึ่งเป็นประตูเชื่อม VPC กับอินเทอร์เน็ต ใน subnet นี้มีเครื่อง tier 1: web + app ที่มี public IP บนเครื่องนี้ Nginx ทำสองงาน งานแรกคือส่งไฟล์หน้าเว็บให้ผู้ใช้ งานที่สองคือเป็น reverse proxy หรือตัวรับคำขอแทนโปรแกรมที่อยู่ข้างหลัง Nginx รับคำขอที่ขึ้นต้นด้วย /api แล้วส่งต่อให้ API ที่รันอยู่ในเครื่องเดียวกันที่ 127.0.0.1:3000 (127.0.0.1 หมายถึงเครื่องตัวเอง) ผู้ใช้จึงคุยกับ Nginx ที่ port 443 อย่างเดียว และไม่เคยคุยกับ API ตรง ๆ

Private subnet 10.0.2.0/24 ไม่มี route ที่ให้อินเทอร์เน็ตเข้ามาได้ ข้างในมีเครื่อง tier 2: database ซึ่งรับการเชื่อมต่อจากเครื่อง tier 1 เท่านั้น แต่ฐานข้อมูลยังต้องออกไปโหลด patch (อัปเดตแก้บั๊กและช่องโหว่) ได้ จึงต้องมี NAT Gateway ซึ่งเป็นตัวแปลง private IP เป็น public IP สำหรับ traffic ขาออก NAT Gateway วางอยู่ใน public subnet และ route table ของ private subnet ส่ง 0.0.0.0/0 ไปที่ NAT Gateway หัวใจของ NAT คือดูว่าใครเริ่มก่อน ถ้าเครื่องข้างในเป็นคนเริ่มขอ คำตอบจะกลับเข้ามาได้ แต่ถ้าคนข้างนอกพยายามเริ่มคุยเข้ามาก่อน NAT จะไม่ยอม

ภาพนี้ใช้ได้ทั้งข้อ 1–2 และข้อ 3–4 เพราะตอบคำถาม "อะไรทำให้ subnet เป็น public" ได้ในตัว คำตอบคือ route ไป IGW ไม่ใช่ชื่อของ subnet และไม่ใช่การที่เครื่องมี public IP

แบบร่างแรกของทีม (Sprint 0 คือรอบวางแผนแรกของโปรเจกต์) จัดสองชั้นอีกแบบ คือวาง web ไว้ใน public และวาง API ไว้กับฐานข้อมูลใน private แบบนั้นก็เป็นสองชั้นเหมือนกัน แต่ไม่ตรงกับนิยาม 2 tier ในสไลด์ ในข้อสอบให้ใช้แบบของสไลด์ที่แยกฐานข้อมูลออกมา เพราะผู้ตรวจจะเทียบกับนิยามนั้น

5. ทำไมวางแบบนี้

หลักข้อแรกคือของที่สำคัญที่สุดอยู่ลึกที่สุด ฐานข้อมูลเก็บข้อมูลผู้ใช้ทั้งหมด จึงอยู่ใน private subnet และรับการเชื่อมต่อจากเครื่อง tier 1 ทางเดียว คนข้างนอกที่อยากได้ข้อมูลต้องผ่าน Nginx ก่อน แล้วต้องผ่าน API ซึ่งตรวจสิทธิ์และตรวจข้อมูลที่ส่งเข้ามาทุกครั้ง ถ้าเว็บถูกเจาะ ผู้โจมตีก็ยังไม่ได้ฐานข้อมูลไปทันที หลักนี้คือ defense in depth (ป้องกันหลายชั้น) ในช่วงที่ 3

หลักข้อที่สองคือเปิดสู่อินเทอร์เน็ตให้น้อยที่สุด ทั้งระบบมีเครื่องเดียวที่มี public IP และเครื่องนั้นเปิดรับแค่ HTTPS (port 443) port 80 เปิดไว้แค่ส่งผู้ใช้ต่อไปที่ 443 ส่วน port 3000 ของ API ไม่ต้องเปิดเลย เพราะ API ฟังแค่ภายในเครื่อง ตอนส่งงาน ทีมใช้ nmap (โปรแกรมสแกนว่าเครื่องเปิด port อะไรบ้าง) สแกนจากข้างนอก เพื่อยืนยันว่าเข้า port ของ API และฐานข้อมูลไม่ได้จริง

หลักข้อที่สามเป็นผลพลอยได้จาก reverse proxy คือไม่ต้องตั้ง CORS CORS (Cross-Origin Resource Sharing) คือกติกาของเบราว์เซอร์ ที่ไม่ยอมให้ JavaScript ของเว็บหนึ่งอ่านคำตอบจากต่าง origin ถ้าปลายทางไม่อนุญาต origin คือโปรโตคอล โดเมน และ port รวมกัน ต่างกันแม้แต่อย่างเดียวก็นับเป็นคนละ origin ในแล็บ WebApp หน้าเว็บกับ API อยู่คนละ port จึงต้องเปิด CORS แต่ในโปรเจกต์นี้หน้าเว็บเรียก /api บนโดเมนเดียวกัน เบราว์เซอร์จึงมองว่าเป็น origin เดียวกัน (อ่านทวนที่ ช่วง 2 ข้อ 12)

หลักข้อที่สี่คือเลือกจำนวน tier ให้พอดีกับขนาดระบบ สไลด์ Week 3 บอกว่า 2 tier เหมาะกับแอปขนาดเล็ก MVP (ระบบรุ่นแรกที่มีแค่ฟีเจอร์หลัก) และเครื่องมือที่ใช้กันภายใน เพราะราคาถูกและดูแลง่าย การแยกฐานข้อมูลออกมายังให้ข้อดีสามข้อ คือฐานข้อมูลไม่ถูกเปิดสู่อินเทอร์เน็ต ขยายฐานข้อมูลแยกได้ และปลอดภัยกว่าการรวมทุกอย่างไว้เครื่องเดียว แต่ก็ยังมีจุดอ่อนสามข้อ ข้อแรก เว็บกับแอปยังอยู่เครื่องเดียวกัน ข้อสอง เครื่องนั้นเป็น single point of failure คือจุดเดียวที่ถ้าพังแล้วทั้งระบบพังตาม ข้อสาม ยังไม่มี load balancer (ตัวรับคำขอแล้วแจกงานให้หลายเครื่อง) จุดอ่อนเหล่านี้จะแก้ในหัวข้อ 9

6. Security Group ที่ต่อกันเป็นชั้น

ในโจทย์ตั้งค่า ส่วนที่ได้คะแนนมากที่สุดคือตารางกฎ SG แบบ 2 tier มี SG สองกลุ่ม คือ tier ละหนึ่งกลุ่ม หัวใจของตารางนี้คือให้ฐานข้อมูลรับ traffic จากชั้นที่อยู่ติดกันเท่านั้น

Security Groupขาเข้า (port)รับจากเหตุผล
sg-web443/tcp0.0.0.0/0ผู้ใช้ทั่วโลกเข้าเว็บผ่าน HTTPS
sg-web80/tcp0.0.0.0/0ใช้แค่ส่งผู้ใช้ต่อไปที่ 443
sg-web22/tcpIP ของทีมให้ผู้ดูแล SSH เข้าไปจัดการ ห้ามเปิดให้ทั้งโลก
sg-db5432/tcpsg-webมีแค่เครื่อง tier 1 ที่คุยกับฐานข้อมูลได้
sg-db22/tcpsg-webผู้ดูแล SSH ต่อจากเครื่อง tier 1 เข้ามาดูแลฐานข้อมูล

สังเกตว่าช่อง "รับจาก" ของ sg-db เขียนเป็นชื่อ SG ไม่ใช่เลข IP การอ้างชื่อ SG แปลว่า "เครื่องไหนก็ได้ที่อยู่ในกลุ่มนั้น" ถ้าวันหลังเพิ่มเครื่อง tier 1 อีกเครื่อง หรือเครื่องเดิมเปลี่ยน IP กฎนี้ก็ยังใช้ได้โดยไม่ต้องแก้ ข้อนี้สำคัญมากเมื่อใช้ Auto Scaling เพราะเครื่องถูกสร้างและลบอยู่ตลอด ส่วนที่ตารางนี้ไม่มี sg-app ก็เพราะ API อยู่เครื่องเดียวกับ Nginx คำขอระหว่างสองโปรแกรมนี้วิ่งอยู่ภายในเครื่อง ไม่ผ่านเครือข่าย

ตารางนี้มีแต่กฎขาเข้า ไม่ต้องเขียนกฎขากลับ เพราะ SG เป็นแบบ stateful คือจำได้ว่าการเชื่อมต่อไหนได้รับอนุญาตแล้ว แล้วปล่อยคำตอบของการเชื่อมต่อนั้นกลับไปเอง แต่ถ้าโจทย์ให้ตั้ง NACL ด้วย ต้องระวัง เพราะ NACL เป็นแบบ stateless คือไม่จำการเชื่อมต่อ จึงต้องเปิดขาออกให้ ephemeral port ด้วย ephemeral port คือ port เลขสูงที่ฝั่งผู้เรียกสุ่มขึ้นมารอรับคำตอบ ถ้าไม่เปิด คำตอบจะออกไปไม่ได้ (อ่านทวนที่ ช่วง 3 ข้อ 2)

เรื่อง SSH (การเข้าไปสั่งงานเครื่องจากระยะไกล) ยังมีแบบที่ดีกว่าการใช้เครื่อง tier 1 เป็นทางผ่าน คือแยก bastion ออกมาเป็นเครื่องของตัวเอง bastion คือเครื่องตัวกลางเครื่องเดียวที่ต้อง SSH ผ่านก่อนจะเข้าเครื่องอื่น อีกทางหนึ่งคือใช้บริการของ Cloud ที่เข้าเครื่องได้โดยไม่ต้องเปิด port 22 เลย

7. กำหนด Instance

เมื่อโจทย์ให้ "กำหนด instance" ต้องบอกหกอย่างของทุกเครื่อง คือทำหน้าที่อะไร อยู่ subnet ไหน มี public IP หรือไม่ ใช้ SG อะไร ขนาดเท่าไร และใช้ที่เก็บข้อมูลแบบไหน ไม่ต้องจำชื่อรุ่นเครื่องของผู้ให้บริการ เขียนเป็นจำนวน vCPU (CPU เสมือนที่ได้รับแบ่งมา) กับขนาด RAM ก็ได้ แต่ต้องบอกเหตุผลว่าทำไมเลือกขนาดนั้น

เครื่องSubnetPublic IPSGขนาดและเหตุผล
Tier 1: Web + App (Nginx, Node.js)Publicมีsg-webขนาดกลาง เช่น 2 vCPU 4 GB เพราะรันทั้งหน้าเว็บและ API
Tier 2: Database (PostgreSQL)Privateไม่มีsg-dbเน้น RAM ไว้ cache ข้อมูล และต้องมีดิสก์แบบ block storage ที่ข้อมูลไม่หายเมื่อปิดเครื่อง

จำนวนเครื่องมาจาก 2 tier โดยตรง คือชั้นละหนึ่งเครื่อง ถ้าโจทย์บอกว่าข้อมูลสำคัญมาก จะใช้ฐานข้อมูลแบบ managed แทนการติดตั้งเองก็ได้ เช่น RDS (Relational Database Service) ซึ่งเป็นฐานข้อมูลที่ผู้ให้บริการดูแลการติดตั้ง แพตช์ และ backup ให้ ส่วนการเลือกที่เก็บข้อมูลใช้หลักเดียวกับ ช่วง 1 ข้อ 19 ดิสก์ของฐานข้อมูลใช้ block storage ไฟล์ที่ผู้ใช้อัปโหลดใช้ object storage และโฟลเดอร์ที่หลายเครื่องต้องใช้ร่วมกันใช้ file storage

8. ของจริงที่ deploy ต่างจากแบบยังไง

ตอนลงมือจริง ทีม deploy (นำระบบขึ้นไปรันจริง) บน ruk-com ซึ่งเป็นผู้ให้บริการ Cloud ในไทย ruk-com ไม่มี VPC กับ subnet ให้ตั้งเองแบบ AWS ทีมจึงต้องใช้กลไกอื่นให้ได้ผลแบบเดียวกัน หัวข้อนี้เป็นตัวอย่างที่ดีว่าเครื่องมือเปลี่ยนได้ แต่แนวคิดยังเหมือนเดิม และนี่คือสิ่งที่ข้อสอบอยากให้เข้าใจ

ของจริงแยกเป็นสองเครื่องเหมือนกัน แต่จัดของคนละแบบกับหัวข้อ 4 เครื่องแรกมีแค่ Nginx ส่วน API ย้ายไปอยู่กับฐานข้อมูลในเครื่องที่สอง แบบนี้ก็ยังเป็นสองชั้น และฐานข้อมูลก็ยังถูกซ่อนเหมือนเดิม ตารางข้างล่างเทียบเฉพาะกลไกที่ใช้

สิ่งที่แบบต้องการแบบบน AWSที่ทำจริงบน ruk-com
ผู้ใช้เข้าได้ทางเดียวweb server มี public IP อยู่ใน public subnetทุกเครื่องไม่มี public IP ผู้ใช้เข้าผ่าน load balancer (ตัวรับคำขอแล้วส่งต่อให้เครื่องข้างใน) ของผู้ให้บริการ
เข้ารหัสด้วย HTTPSติดตั้ง certificate บน Nginx เองload balancer ถอดรหัส TLS (Transport Layer Security ชั้นเข้ารหัสของ HTTPS) ให้ แล้วส่งต่อเป็น HTTP ภายในเครือข่ายส่วนตัว
ฐานข้อมูลไม่ให้ข้างนอกเห็นฐานข้อมูลอยู่ใน private subnet ที่ไม่มี route จากเน็ตแยกเป็นสองเครื่องที่คุยกันด้วย private IP ฐานข้อมูลฟังแค่ 127.0.0.1 จึงรับได้แค่จากในเครื่องตัวเอง
เครื่องหลังบ้านรับจากเครื่อง web เท่านั้นsg-db รับจาก sg-webiptables (firewall ที่มากับ Linux แบบในแล็บ Build VPC) บนเครื่องหลังบ้านรับ port 3000 จาก IP ของเครื่อง web เท่านั้น และตัว API ตรวจ IP ซ้ำอีกชั้น
ผู้ดูแลเข้าเครื่องได้ทางเดียวSSH จาก IP ของทีม หรือผ่าน bastionSSH ผ่าน gate ของผู้ให้บริการด้วย key เท่านั้น ซึ่งทำหน้าที่เหมือน bastion

นอกจากเรื่องเครือข่าย ทีมยังใช้หลัก Least Privilege (ให้สิทธิ์เท่าที่จำเป็นเท่านั้น) ในระดับเครื่องด้วย มีสามเรื่อง เรื่องแรก API รันในชื่อผู้ใช้ที่ไม่ใช่ root (ผู้ใช้ที่มีสิทธิ์สูงสุดของ Linux) และเขียนไฟล์ระบบไม่ได้ ถ้าโปรแกรมถูกเจาะ คนร้ายก็ได้สิทธิ์แค่เท่านั้น เรื่องที่สอง ฐานข้อมูลยืนยันตัวตนจากชื่อผู้ใช้ของระบบปฏิบัติการ จึงไม่มีรหัสผ่านฐานข้อมูลให้หลุด เรื่องที่สาม ค่าลับ (secret) เช่น กุญแจที่ใช้เซ็น token (บัตรผ่านที่บอกว่าผู้ใช้ล็อกอินแล้ว) เก็บอยู่ในไฟล์บนเครื่อง API ที่อ่านได้เฉพาะ root กับผู้ใช้ของ API และไม่ได้อยู่ใน Git

เรื่อง backup ทีมสั่ง dump ฐานข้อมูล (ส่งออกข้อมูลทั้งหมดเป็นไฟล์) ทุกวันตอนตีสาม และเก็บย้อนหลังเจ็ดวัน ทีมทดสอบกู้คืนแล้ว และเช็กว่าจำนวนแถวตรงกับของจริง ที่ต้องทดสอบก็เพราะ backup ที่ไม่เคยลองกู้คืน ก็ยังไม่รู้ว่าใช้ได้จริงหรือเปล่า แต่รายงานของทีมก็ยอมรับข้อจำกัดไว้เองสองข้อ ข้อแรก backup ยังอยู่บนเครื่องเดียวกับฐานข้อมูล ถ้ายังไม่ได้ดึงออกไปเก็บที่อื่นแล้วเครื่องเสีย backup ก็หายไปด้วย ข้อที่สอง ทั้งระบบมีอย่างละหนึ่งเครื่อง เครื่องไหนล่ม ระบบก็ล่ม ข้อจำกัดสองข้อนี้คือสิ่งที่หัวข้อถัดไปจะแก้

9. ขยายแบบให้ทนเมื่อ AZ หนึ่งล่ม

หัวข้อ 9 และ 10 เป็นส่วนเสริมสำหรับคนที่อยากรู้มากกว่าที่ข้อสอบถาม ถ้าเวลาน้อย ให้ฝึกวาดภาพในหัวข้อ 4 และเขียนตารางในหัวข้อ 6–7 จากความจำให้ได้ก่อน แล้วไปฝึกทำข้อสอบที่ ช่วงที่ 6 จากหัวข้อ 9 ขอให้จำแค่ประโยคเดียว คือ ถ้าไม่อยากให้ระบบล่ม ให้กระจายทุกชั้นไปสอง AZ วาง load balancer ไว้หน้า app server หลายเครื่อง และให้ฐานข้อมูลมีตัวสำรอง

ถ้าโจทย์มีคำว่า "ห้ามล่ม" "high availability" (ระบบที่ใช้งานได้ตลอด ไม่ล่ม) หรือ "รองรับผู้ใช้จำนวนมาก" แบบ 2 tier สองเครื่องในหัวข้อ 4 จะไม่พอ ต้องขยับไปเป็น 3 tier เพราะทุกชั้นยังเป็น single point of failure (จุดเดียวที่ถ้าเสียแล้วทั้งระบบเสีย) วิธีแก้คือให้ทุกชั้นมีอย่างน้อยสองชุด และวางไว้คนละ AZ ตามหลักการวาง subnet ในสไลด์ Week 3

ชั้นหน้าบ้านเปลี่ยนจาก web server เครื่องเดียวที่มี public IP มาเป็น ALB (Application Load Balancer) ซึ่งเป็นตัวรับคำขอ HTTP/HTTPS แล้วกระจายไปให้หลายเครื่อง ALB วางคร่อม public subnet ของทั้งสอง AZ และคอยตรวจสุขภาพ (health check) ของเครื่องข้างหลังเป็นระยะ ถ้าเครื่องไหนไม่ตอบ ALB ก็หยุดส่งงานให้เครื่องนั้น เมื่อผู้ใช้เข้ามาทาง ALB แล้ว app server ก็ไม่ต้องมี public IP อีกต่อไป และย้ายเข้าไปอยู่ใน private subnet ได้ทั้งหมด

ชั้นแอปใช้ Auto Scaling group (ASG) คือกลุ่มเครื่องที่ระบบเพิ่มหรือลดจำนวนให้เอง ตั้งจำนวนขั้นต่ำไว้สองเครื่อง AZ ละหนึ่งเครื่อง เพื่อให้ AZ หนึ่งล่มแล้วยังเหลืออีกเครื่อง และตั้งจำนวนสูงสุดไว้รับช่วงที่คนเข้าเยอะ เครื่องในกลุ่มนี้ต้องเป็นแบบ stateless คือไม่เก็บข้อมูลของผู้ใช้ไว้ในตัวเอง เพราะคำขอถัดไปของผู้ใช้คนเดิมอาจไปตกที่เครื่องอื่น หรือเครื่องอาจถูกลบทิ้งตอนลดจำนวน ข้อมูลทั้งหมดจึงต้องเก็บไว้ในฐานข้อมูล

ชั้นข้อมูลมีฐานข้อมูลหลักอยู่ใน AZ หนึ่ง และฐานข้อมูลสำรองอยู่อีก AZ ตัวสำรองรับสำเนาข้อมูลจากตัวหลักตลอดเวลา ถ้าตัวหลักล่ม ระบบจะสลับไปใช้ตัวสำรองแทน subnet ของฐานข้อมูลไม่มี route ออกอินเทอร์เน็ตเลย ทั้งขาเข้าและขาออก เพราะฐานข้อมูลไม่ต้องคุยกับใครนอกจาก app server

ส่วน NAT Gateway ใช้ AZ ละหนึ่งตัว และ route table ของ app subnet ในแต่ละ AZ ชี้ไปที่ NAT ของ AZ ตัวเอง ถ้าใช้ NAT ตัวเดียว เมื่อ AZ ที่มี NAT ล่ม เครื่องใน AZ ที่เหลือก็จะออกเน็ตไม่ได้ไปด้วย

การแบ่ง CIDR ใช้หลักจากสไลด์ คือ public subnet เล็กได้ เพราะของที่หันออกเน็ตมีไม่กี่ตัว ส่วน private subnet ควรใหญ่กว่า เพราะเครื่องส่วนใหญ่อยู่ที่นั่น แต่ภาพนี้ใช้ /24 ทุก subnet เพื่อให้อ่านง่าย และตั้งเลขชุดที่สามให้บอก tier ได้ทันที (1–2 เป็น public, 11–12 เป็น app, 21–22 เป็น db) แต่ละ /24 มี 232−24 = 256 ที่อยู่ AWS จองไว้ 5 ตัวต่อ subnet จึงเหลือให้เครื่องใช้ 251 ตัว ส่วน VPC /16 มี 65,536 ที่อยู่ จึงยังเหลือที่ให้เพิ่ม subnet ได้อีกมาก

10. ฝึกตอบโจทย์หนึ่งข้อ

โจทย์ตัวอย่าง: มหาวิทยาลัยต้องการย้ายระบบลงทะเบียนเรียนขึ้น Cloud ช่วงเปิดลงทะเบียนมีนักศึกษาเข้าพร้อมกันหลายหมื่นคน แต่ช่วงอื่นใช้น้อยมาก ระบบห้ามล่มระหว่างเปิดลงทะเบียน ข้อมูลนักศึกษาห้ามรั่ว และผู้ดูแลระบบต้องเข้าไปจัดการเครื่องได้ ให้ออกแบบ architecture กำหนด instance และการตั้งค่าที่สำคัญ

อ่านความต้องการก่อน "เข้าพร้อมกันเป็นช่วง" แปลว่าต้องใช้ Auto Scaling แทนการซื้อเครื่องใหญ่ไว้ทั้งปี ข้อนี้ตรงกับลักษณะ rapid elasticity ของ Cloud (ขยายและหดได้เร็วตามความต้องการ) "ห้ามล่ม" แปลว่าทุกชั้นต้องอยู่สอง AZ "ข้อมูลห้ามรั่ว" แปลว่าฐานข้อมูลต้องอยู่ใน private subnet ที่ไม่มี route ออกเน็ต และต้องเข้ารหัสข้อมูล ส่วน "ผู้ดูแลต้องเข้าได้" แปลว่าต้องมีทางเข้าทางเดียวที่ควบคุมได้ ซึ่งก็คือ bastion

โครงสร้าง ใช้แบบของหัวข้อ 9 ทั้งหมด คือ VPC 10.0.0.0/16 กระจายสอง AZ แต่ละ AZ มี public, app และ db subnet มี ALB คร่อม public subnet มี NAT Gateway AZ ละหนึ่งตัว และเพิ่ม bastion หนึ่งเครื่องใน public subnet ถ้าโจทย์บอกว่ามหาวิทยาลัยมีเครือข่ายเดิมที่ต้องเชื่อมเข้ามา ก็เพิ่ม Site-to-Site VPN (อุโมงค์เข้ารหัสที่วิ่งผ่านอินเทอร์เน็ต) หรือ Direct Connect (สายเชื่อมตรงที่ไม่ผ่านอินเทอร์เน็ต) ตาม ช่วง 3 ข้อ 4

สังเกตว่าคำตอบนี้ก็คือแบบของโปรเจกต์ "คันนี้ดีไหม?" ที่ขยายใหญ่ขึ้น สิ่งที่เปลี่ยนคือขยับจาก 2 tier เป็น 3 tier โดยแยก app server ออกจากเครื่อง web เปลี่ยนเครื่องหน้าบ้านเครื่องเดียวเป็น ALB คู่กับ ASG ให้ฐานข้อมูลมีตัวสำรอง และย้าย backup ออกจากเครื่องฐานข้อมูล ทุกอย่างที่เปลี่ยนคือการแก้ข้อจำกัดที่รายงานของทีมยอมรับไว้เอง ถ้าเจอโจทย์อื่น ก็ให้เริ่มจากแบบ 2 tier ของโปรเจกต์ แล้วเพิ่มชิ้นส่วนตามคำในโจทย์ทีละอย่าง

ถ้าอยากลองทำข้อสอบครบทั้ง 4 ข้อแบบข้อเขียน มีชุดตัวอย่างพร้อมแนวคำตอบอยู่ใน ช่วงที่ 6

ทวนก่อนสอบ

ข้อ 1–2 ให้ตอบสามขั้น คือนิยาม เหตุผล และตัวอย่าง เรื่องที่ต้องแม่นที่สุดคือลักษณะ 5 ข้อของ Cloud, IaaS/PaaS/SaaS, Region กับ AZ, การคำนวณ CIDR (อย่าลืมลบ 5 สำหรับ AWS) และความต่างของ public กับ private subnet ซึ่งต่างกันที่ route ไป IGW เพียงอย่างเดียว

ข้อ 3–4 อาจารย์กำหนดให้โปรเจกต์เป็น 2 tier คือ web + app อยู่ใน public subnet และฐานข้อมูลแยกไปอยู่ใน private subnet ให้ตอบตามลำดับนี้ ความต้องการ → tier → VPC และ subnet → route table → instance → SG และ NACL → IAM, backup และการเข้าดูแลเครื่อง แล้วปิดด้วยการไล่เส้นทาง traffic ทุกตารางต้องมีคอลัมน์เหตุผล และทุกการตัดสินใจต้องโยงกลับไปหาคำในโจทย์ได้

กับดักในโจทย์ออกแบบที่ควรระวังมีแปดข้อ (1) เครื่องที่มี public IP ไม่ได้ทำให้ subnet เป็น public ถ้าไม่มี route ไป IGW (2) NAT Gateway ต้องอยู่ใน public subnet ไม่ใช่ private (3) ฐานข้อมูลไม่ควรมี public IP และต้องอยู่ใน private subnet (4) ห้ามเปิด port 22 ให้ 0.0.0.0/0 (5) กฎ SG ระหว่าง tier ควรอ้างชื่อ SG ไม่ใช่ IP (6) SG ไม่ต้องเขียนกฎขากลับ แต่ NACL ต้องเปิด ephemeral port (7) "ห้ามล่ม" ต้องใช้อย่างน้อยสอง AZ ทั้งชั้นแอปและชั้นข้อมูล (8) NAT ตัวเดียวก็เป็น single point of failure ได้
