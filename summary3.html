ช่วงนี้ต้องเข้าใจอะไร

ช่วงนี้ตอบคำถามสามข้อ ข้อแรก ใครรับผิดชอบส่วนไหน (shared responsibility) ข้อสอง packet ผ่านด่านได้หรือไม่ ซึ่งต้องเข้าใจความต่างระหว่าง Security Group ที่จำการเชื่อมต่อได้กับ NACL ที่จำไม่ได้ และไล่กฎของ NACL ตามเลขได้ ข้อสาม คนหรือโปรแกรมมีสิทธิ์ทำสิ่งนั้นไหม ซึ่งต้องไล่ตรรกะของ IAM ให้เป็น คือ Deny ชนะเสมอ และถ้าไม่มีกฎพูดถึงก็ถือว่าห้าม ที่เหลือคือการเชื่อมออฟฟิศเข้ากับ Cloud การป้องกันหลายชั้น (Defense in Depth) และหลักการออกแบบ 8 ข้อ ซึ่งข้อสอบมักให้สถานการณ์มาแล้วถามว่าตรงกับหลักข้อไหน

1. Shared Responsibility: ใครดูแลความปลอดภัยส่วนไหน

ความปลอดภัยบน Cloud เป็นงานของสองฝ่าย ผู้ให้บริการดูแลส่วนที่ลูกค้าแตะไม่ได้ เช่น อาคาร data center เครื่อง server ไฟฟ้า และ hypervisor (ซอฟต์แวร์ที่แบ่งเครื่องจริงหนึ่งเครื่องออกเป็นหลาย VM) เรียกว่า Security OF the Cloud ลูกค้าดูแลทุกอย่างที่ตัวเองตั้งค่า เช่น ข้อมูล สิทธิ์ผู้ใช้ OS และแอป กฎ firewall และการเข้ารหัส เรียกว่า Security IN the Cloud

หลักจำคือ ใครเป็นคนตั้งค่าสิ่งไหน คนนั้นรับผิดชอบสิ่งนั้น เช่น ถ้าบริษัทตั้งถังเก็บไฟล์ (S3 bucket) ให้ใครก็เปิดอ่านได้แล้วข้อมูลลูกค้ารั่ว ความผิดเป็นของบริษัท เพราะผู้ให้บริการไม่รู้ว่าบริษัทตั้งใจเปิดหรือเปล่า

เส้นแบ่งเลื่อนตามประเภทบริการ ใน IaaS ลูกค้าดูแลตั้งแต่ OS ขึ้นไปรวมถึงลง patch (ตัวแก้ช่องโหว่) เอง ใน PaaS ผู้ให้บริการดูแล OS ให้ ลูกค้าดูแลแค่แอปกับข้อมูล ใน SaaS ลูกค้าดูแลน้อยที่สุด แต่เรื่องข้อมูลและสิทธิ์การเข้าถึงยังเป็นงานร่วมกัน เพราะการแชร์ไฟล์ให้ใคร การเปิด MFA (Multi-Factor Authentication การยืนยันตัวตนหลายขั้น เช่น รหัสผ่านบวกรหัสจากมือถือ) หรือการปิดบัญชีพนักงานที่ลาออก ล้วนเป็นการตัดสินใจของลูกค้า สองเรื่องที่ไม่เปลี่ยนเลยคือ เครื่องจริงกับ hypervisor เป็นหน้าที่ผู้ให้บริการเสมอ และข้อมูลของลูกค้าไม่เคยเป็นหน้าที่ของผู้ให้บริการฝ่ายเดียว

AWS กับ Azure มีเครื่องมือด้านความปลอดภัยครบเหมือนกัน ต่างกันแค่ชื่อ คู่ที่ควรรู้คือ Security Group ของ AWS ตรงกับ NSG (Network Security Group) ของ Azure, IAM ตรงกับ Entra ID และ Direct Connect ตรงกับ ExpressRoute

2. Security Group และ Network ACL

AWS มี firewall ที่ตั้งค่าเองได้สองชนิด วางคนละตำแหน่ง Security Group (SG) ติดอยู่กับเครื่องแต่ละเครื่อง ส่วน NACL (Network Access Control List รายการควบคุมการเข้าถึงระดับเครือข่าย เรียกสั้น ๆ ว่า Network ACL) ตั้งอยู่ที่ขอบ subnet และตรวจทุกอย่างที่เข้าออก subnet นั้น packet จากอินเทอร์เน็ตจึงต้องผ่าน NACL ก่อน แล้วค่อยถึง SG ของเครื่องปลายทาง NACL คือยามที่ประตูหมู่บ้าน ส่วน SG คือกุญแจประตูของแต่ละบ้าน

ความต่างที่สำคัญที่สุดคือเรื่องความจำ SG เป็นแบบ stateful หมายถึงจดการเชื่อมต่อที่ปล่อยเข้ามาไว้ เมื่อเครื่องส่งคำตอบกลับออกไป SG รู้ว่าเป็นคำตอบของคำขอเดิมจึงปล่อยออกเองโดยไม่ต้องมีกฎขาออก เขียนแค่กฎขาเข้าก็พอ (เหมือนกฎ ESTABLISHED,RELATED ของ iptables ซึ่งเป็น firewall ในตัว Linux ที่ใช้ในแล็บ) ส่วน NACL เป็นแบบ stateless ไม่จำอะไรเลย มองทุก packet เป็นของใหม่ คำตอบขากลับจึงต้องมีกฎขาออกเปิดไว้แยกต่างหาก

แล้วกฎขาออกต้องเปิด port อะไร คำตอบไม่ใช่ 80 หรือ 443 เพราะคำตอบไม่ได้วิ่งกลับไปที่ port ของบริการ แต่วิ่งกลับไปที่ port เลขสูงที่เครื่องผู้ใช้สุ่มขึ้นมาตอนเปิดการเชื่อมต่อ เรียกว่า ephemeral port (port ชั่วคราว) เครื่องผู้ใช้ต้องสุ่มเลขนี้เพราะเปิดหลายการเชื่อมต่อพร้อมกัน เช่น เปิดเว็บหลายแท็บ แต่ละเส้นจึงต้องมีเลขของตัวเองไม่ซ้ำกัน คำตอบจะได้กลับมาถูกเส้น

ลองไล่ตัวอย่าง เครื่องผู้ใช้สุ่มได้ port 50123 แล้วส่งคำขอไปที่ port 443 ของ server ขาเข้านี้ NACL ต้องเปิด 443 พอ server ตอบกลับ คำตอบจะออกจาก port 443 ไปที่ port 50123 ของผู้ใช้ ขาออกนี้ NACL จึงต้องเปิด 50123 ด้วย และเพราะผู้ใช้คนถัดไปอาจสุ่มได้เลขอื่น เราจึงต้องเปิดไว้ทั้งช่วงของ port เลขสูง ถ้าลืมเปิด คำขอไปถึง server ได้ แต่คำตอบกลับไม่ถึงผู้ใช้

เรื่องเดียวกันเกิดได้ในทิศกลับ ถ้าเครื่องของเราเป็นฝ่ายเริ่มเชื่อมต่อออกไปเอง เช่น ออกไปโหลดอัปเดต เครื่องเราจะเป็นฝ่ายสุ่ม port และคำตอบจะวิ่งกลับเข้ามาที่ port เลขสูงของเรา NACL ก็ต้องเปิดช่วงนั้นในขาเข้าด้วย หลักจำคือ กับ NACL ทุกการเชื่อมต่อต้องคิดสองขาเสมอ ขาไปเปิด port ของบริการ ขากลับเปิดช่วง ephemeral port

NACL ไล่กฎแบบนี้ เริ่มจากกฎเลขน้อยที่สุด เจอกฎแรกที่ตรงก็ทำตามทันทีแล้วหยุด ไม่ว่าจะเป็นอนุญาตหรือห้าม ถ้าไม่ตรงข้อไหนเลยจะไปเจอกฎท้ายสุด (*) ที่ห้ามทุกอย่าง ผลคือถ้ากฎห้ามไปอยู่หลังกฎอนุญาตที่กว้างกว่า กฎห้ามนั้นไม่มีผลเลย เพราะ packet ไปตรงกฎอนุญาตก่อน กฎที่เจาะจงจึงต้องได้เลขน้อยกว่ากฎที่กว้าง และควรเว้นเลขกฎเป็นช่วง เช่น 50, 80, 100 ไม่ใช่ 1, 2, 3 จะได้แทรกกฎเจาะจงไว้หน้ากฎกว้างได้ภายหลัง อีกข้อคือ NACL ไม่ตรวจ traffic ที่คุยกันภายใน subnet เดียวกัน เพราะไม่ได้ข้ามขอบ subnet

ข้อดีของ SG ที่ NACL ไม่มีคือ อ้างต้นทางเป็น SG อีกตัวได้ เช่น ให้ฐานข้อมูลรับเฉพาะจากเครื่องที่อยู่ใน SG ของกลุ่ม app แทนการเขียน IP ตรง ๆ ถ้าเครื่อง app เปลี่ยน IP หรือ Auto Scaling (ระบบเพิ่มลดเครื่องอัตโนมัติ) เพิ่มเครื่องใหม่ กฎก็ยังใช้ได้โดยไม่ต้องแก้ เพราะกฎดูว่าเครื่องอยู่ใน SG ไหน ไม่ได้ดู IP

ทั้งสองด่านทำงานร่วมกันชัดที่สุดในเว็บแบบ three-tier ชั้นหน้าบ้านคือ ALB (Application Load Balancer ตัวรับคำขอแล้วกระจายไปยังเครื่อง app หลายเครื่อง) อยู่ใน public subnet ชั้นกลางคือเครื่อง app และชั้นในสุดคือฐานข้อมูล สองชั้นหลังอยู่ใน private subnet ฐานข้อมูลจึงไม่มีทางรับคำขอจากอินเทอร์เน็ตตรง ๆ ทุกชั้นมีทั้ง NACL ที่ตรวจจากช่วง IP ของ subnet ต้นทาง และ SG ที่ตรวจจาก SG ของต้นทาง คำขอต้องผ่านทั้งสองด่านในทุกชั้นที่วิ่งผ่าน (ในภาพ 0.0.0.0/0 หมายถึงทุก IP บนอินเทอร์เน็ต)

3. IAM: ใครทำอะไรได้บ้าง

IAM (Identity and Access Management) คือระบบที่ตัดสินว่าใครทำอะไรกับทรัพยากรชิ้นไหนได้บ้าง ทุกอย่างที่ทำบน AWS ไม่ว่าจะกดปุ่มในหน้าเว็บหรือรันคำสั่ง สุดท้ายแล้วคือการเรียก API ของ AWS หนึ่งครั้ง (API หรือ Application Programming Interface คือช่องทางที่โปรแกรมใช้สั่งงานบริการ) และทุกครั้ง IAM จะดูสามส่วน คือ Principal (ใครเป็นคนขอ), Policy (เอกสารที่เขียนว่าทำอะไรได้หรือไม่ได้) และ Resource (ทำกับของชิ้นไหน)

ทรัพยากรแต่ละชิ้นระบุด้วยชื่อเต็มที่ไม่ซ้ำกันเรียกว่า ARN (Amazon Resource Name) เช่น arn:aws:s3:::my-app-bucket หมายถึง bucket ชื่อ my-app-bucket ในบริการ S3

ตัวตนมีสามแบบ User คือบัญชีของคนหรือโปรแกรม มีรหัสผ่านหรือ access key (คู่รหัสที่โปรแกรมใช้เรียก API แทนการ login) ที่ใช้ได้ถาวรจนกว่าจะลบ Group คือกลุ่มของ user มีไว้ผูก policy ทีเดียวให้ทุกคนในกลุ่ม Role คือตัวตนที่ไม่มีรหัสถาวร ผู้ที่ได้รับอนุญาตจะ "สวม" role ชั่วคราวแล้วได้ key ที่หมดอายุเอง ต่อให้ key หลุดก็ใช้ได้ไม่นาน role จึงเหมาะกับเครื่องหรือโปรแกรมที่ต้องเรียกบริการอื่น การให้คนจากบัญชี AWS อื่นเข้ามาใช้ และการ login ผ่านระบบขององค์กร

แนวปฏิบัติที่ดีคือไม่ใช้บัญชี root (เจ้าของที่มีสิทธิ์ทุกอย่าง) ทำงานประจำวัน ไม่ฝัง access key ไว้ในโค้ด เปิด MFA ให้ทุกคน ผูก policy ผ่าน group แทนการผูกกับ user ทีละคน และให้ EC2 (บริการเช่า VM ของ AWS) หรือ Lambda (บริการรันโค้ดโดยไม่ต้องดูแลเครื่อง) ใช้ role แทนการเก็บ access key ไว้ในเครื่อง

Policy เขียนเป็น JSON (รูปแบบข้อความที่เก็บข้อมูลเป็นคู่ของชื่อกับค่า เช่น "Effect": "Allow") ข้อสอบอาจยก policy มาให้อ่าน จึงต้องอ่านให้ออก ดูตัวอย่างจากสไลด์ (ตัดบางบรรทัดออก)

"Statement": [
  {
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": ["arn:aws:s3:::my-app-bucket", "arn:aws:s3:::my-app-bucket/*"]
  },
  {
    "Effect": "Deny",
    "Action": "rds:*",
    "Resource": "arn:aws:rds:*:*:db:prod-*"
  }
]

แต่ละกฎมี Effect (Allow หรือ Deny), Action (ทำอะไร เขียนเป็น บริการ:การกระทำ), Resource (มีผลกับอะไร) และอาจมี Condition (เงื่อนไขเพิ่ม เช่น ต้อง login ด้วย MFA) กฎแรกอนุญาตให้ดูรายชื่อไฟล์และอ่านไฟล์ใน bucket ชื่อ my-app-bucket ที่ Resource มีสองตัวเพราะการดูรายชื่อเป็นการกระทำกับตัว bucket ส่วนการอ่านไฟล์เป็นการกระทำกับไฟล์ข้างใน (bucket/*) กฎที่สองห้ามทุกการกระทำกับฐานข้อมูลที่ชื่อขึ้นต้นด้วย prod- (rds คือบริการฐานข้อมูลของ AWS และ * แปลว่าอะไรก็ได้)

IAM ตัดสินด้วยสามขั้น ซึ่งเป็นเรื่องที่ออกสอบบ่อยที่สุดของหัวข้อนี้ ขั้นแรก ถ้ามี Deny ที่ตรงกับคำขอ ห้ามทันทีไม่ว่าจะมี Allow ด้วยหรือไม่ เรียกว่า explicit deny ขั้นที่สอง ถ้าไม่มี Deny แต่มี Allow ที่ตรง จึงอนุญาต ขั้นที่สาม ถ้าไม่มีกฎไหนพูดถึงคำขอนี้เลยก็ห้าม เรียกว่า implicit deny ผลที่ตามมาคือลำดับการเขียนกฎไม่มีผล (ต่างจาก NACL ที่ไล่ตามเลข) และ user ที่เพิ่งสร้างยังไม่มี policy จะทำอะไรไม่ได้สักอย่าง

Least Privilege คือให้สิทธิ์เท่าที่จำเป็นจริง ๆ เช่น แทนที่จะให้ policy สำเร็จรูป AmazonS3FullAccess ซึ่งอ่าน เขียน และลบได้ทุก bucket ในบัญชี ก็เขียน policy เองว่าอ่านได้แค่ my-app-bucket/images/* และเขียนได้แค่ my-app-bucket/logs/* ที่เหลือทั้งหมดถูก implicit deny ไปเอง วิธีหาสิทธิ์ขั้นต่ำคือเริ่มจากไม่ให้อะไรเลย ลองใช้งาน ติด error AccessDenied (ไม่มีสิทธิ์) ตรงไหนก็เพิ่มเฉพาะสิทธิ์นั้น วนจนใช้งานได้ครบ ห้ามใช้ *:* ซึ่งแปลว่าทำได้ทุกอย่างกับทุกอย่าง

ฝั่ง Azure แยกเป็นสองส่วน Entra ID (ชื่อเดิม Azure AD) เก็บว่าใครเป็นใคร ส่วน RBAC (Role-Based Access Control การให้สิทธิ์ตามบทบาท) ให้สิทธิ์โดยจับคู่สามอย่าง คือ ใคร มีบทบาทอะไร และมีผลในขอบเขตไหน บทบาทสำเร็จรูปที่ใช้บ่อยคือ Owner (ทำได้ทุกอย่างรวมถึงแจกสิทธิ์), Contributor (แก้ไขได้แต่แจกสิทธิ์ไม่ได้) และ Reader (ดูได้อย่างเดียว) ซึ่งเอาไปผูกได้ในขอบเขตที่ซ้อนกันจากกว้างไปแคบสี่ระดับ คือ management group, subscription, resource group (กลุ่มทรัพยากร) และทรัพยากรชิ้นเดียว สิทธิ์ที่ให้ในขอบเขตกว้างจะมีผลกับทุกอย่างข้างใต้ เช่น ให้สิทธิ์อ่านที่ระดับกลุ่มทรัพยากร ก็อ่านได้ทุกชิ้นในกลุ่มนั้น ระวังว่าคำว่า role ของสองเจ้าไม่ใช่ของชนิดเดียวกัน role ของ AWS เป็นตัวตนที่สวมได้ ส่วน role ของ Azure เป็นชุดสิทธิ์ที่เอาไปผูกกับตัวตน

4. เชื่อมเครือข่ายบริษัทเข้ากับ Cloud: VPN และ Direct Connect

ถ้าอยากให้เครื่องในออฟฟิศคุยกับเครื่องใน VPC เหมือนอยู่เครือข่ายเดียวกัน มีสองทาง ทางแรกคือ Site-to-Site VPN (Virtual Private Network เครือข่ายส่วนตัวเสมือน) สร้าง "อุโมงค์" ที่เข้ารหัสด้วย IPsec (IP Security มาตรฐานการเข้ารหัส packet ทุกตัวที่วิ่งผ่านอุโมงค์) ให้วิ่งผ่านอินเทอร์เน็ตธรรมดา คนที่ดักข้อมูลระหว่างทางก็อ่านไม่ออก อุโมงค์มีปลายสองฝั่ง ฝั่งบริษัทคือ Customer Gateway (CGW) หมายถึงอุปกรณ์ VPN หรือ router ของบริษัทที่มี public IP ฝั่ง VPC คือ Virtual Private Gateway (VGW) และ AWS ให้อุโมงค์สองเส้นเสมอ ถ้าเส้นหนึ่งล่ม อีกเส้นยังใช้ได้ นอกจากนี้ route table ของ VPC ต้องมีเส้นทางที่ชี้ไปยังเครือข่ายบริษัทผ่าน VGW ด้วย ไม่อย่างนั้น packet จะไม่รู้ว่าต้องเข้าอุโมงค์ (ดูเรื่อง route table ในช่วงที่ 2)

ทางที่สองคือ Direct Connect (เรียกย่อว่า DX ส่วน Azure เรียกว่า ExpressRoute) ซึ่งเดินสายไฟเบอร์เฉพาะของบริษัทไปต่อกับเครือข่ายส่วนตัวของผู้ให้บริการ ข้อมูลจึงวิ่งไปถึง VPC โดยไม่แตะอินเทอร์เน็ตเลย

Site-to-Site VPNDirect Connect / ExpressRoute
วิ่งผ่านอินเทอร์เน็ตสาธารณะ (เข้ารหัส)สายไฟเบอร์ส่วนตัว
แบนด์วิดท์ (ปริมาณข้อมูลต่อวินาที)ต่ำกว่าสูงกว่ามาก
ความหน่วง (latency)ไม่แน่นอน แกว่งเพราะใช้เน็ตร่วมกับคนอื่นต่ำและคงที่
สัญญารับประกันคุณภาพ (SLA, Service Level Agreement)ไม่มีมี
เวลาติดตั้งไม่กี่นาทีหลายสัปดาห์ เพราะต้องเดินสายจริง
ราคาถูกแพงกว่ามาก
เข้ารหัสไหมเข้ารหัสไม่เข้ารหัสให้เอง

ทางเลือกที่ดีที่สุดสำหรับระบบจริงคือใช้ทั้งสองทาง ให้ Direct Connect เป็นเส้นหลักเพราะเร็วและนิ่ง ให้ VPN เป็นเส้นสำรองเพราะถูกและตั้งทิ้งไว้ได้ แล้วให้ BGP (กติกาที่ router ใช้บอกกันว่าไปทางไหนได้ จากช่วงที่ 2) สลับไปเส้นสำรองเองเมื่อเส้นหลักขาด กับดักที่ต้องจำคือ Direct Connect ไม่ได้เข้ารหัสให้ แม้จะเป็นสายส่วนตัว ถ้าต้องการความลับต้องเข้ารหัสเพิ่มเอง

5. Defense in Depth: ป้องกันหลายชั้น

ไม่มีด่านไหนกันได้ร้อยเปอร์เซ็นต์ firewall อาจตั้งพลาด รหัสผ่านอาจหลุด โค้ดอาจมีช่องโหว่ Defense in Depth จึงวางด่านหลายชั้นที่ทำงานแยกจากกัน ถ้าชั้นหนึ่งพลาด ชั้นถัดไปยังรับไว้ได้ เหมือนบ้านที่มีทั้งรั้ว ประตูล็อก กล้องวงจรปิด และตู้เซฟ สไลด์แบ่งไว้เจ็ดชั้น

ชั้นปกป้องอะไรตัวอย่าง
1 Perimeterขอบของเครือข่ายNACL, ระบบกัน DDoS (Distributed Denial of Service การระดมยิงคำขอจากหลายเครื่องพร้อมกันให้ระบบล่ม)
2 Resourceตัวเครื่องและบริการแต่ละตัวSecurity Group, WAF (Web Application Firewall ตัวอ่านเนื้อหาคำขอ HTTP เพื่อกรองคำขอที่โจมตีเว็บ)
3 Identityตัวตนและสิทธิ์IAM, MFA, SSO (Single Sign-On ล็อกอินครั้งเดียวใช้ได้หลายระบบ)
4 Dataต่อให้ข้อมูลหลุดก็อ่านไม่ออกเข้ารหัสข้อมูลที่เก็บด้วยกุญแจจาก KMS (Key Management Service บริการจัดการกุญแจเข้ารหัส) และเข้ารหัสระหว่างส่งด้วย TLS (Transport Layer Security โปรโตคอลที่ทำให้ https ปลอดภัย)
5 Applicationโค้ดของเราเองตรวจข้อมูลที่ผู้ใช้ส่งเข้ามา และใช้ parameterized query (ส่งค่าที่ผู้ใช้กรอกแยกจากตัวคำสั่ง) กันการแอบใส่คำสั่งฐานข้อมูลมาในช่องกรอก (SQL injection)
6 Monitoringรู้ตัวว่ากำลังโดนโจมตีCloudTrail บันทึกทุกการเรียก API, GuardDuty ตรวจจับพฤติกรรมน่าสงสัย, Security Hub รวมผลตรวจไว้ที่เดียว
7 Incidentรับมือและกู้คืนเมื่อโดนแล้วตอบสนองอัตโนมัติ, backup

ระวังเรื่อง WAF เพราะสไลด์วางไว้ไม่ตรงกันสามที่ คือชั้น Resource ในรายการเจ็ดชั้น ชั้น Perimeter ในภาพที่มีผู้โจมตี และแถว Application ในตารางรายการตรวจ ที่เป็นแบบนี้เพราะ WAF ตั้งอยู่หน้าเว็บเหมือนด่านขอบนอก แต่สิ่งที่ตรวจคือเนื้อหาคำขอ HTTP ซึ่งเป็นเรื่องของแอป ถ้าข้อสอบถามตามรายการเจ็ดชั้นให้ตอบชั้น Resource คู่กับ SG และถ้าถามว่า WAF กันอะไร ให้ตอบว่ากันการโจมตีระดับแอป เช่น SQL injection

สังเกตว่าห้าชั้นแรก (สีฟ้า) มีไว้กัน ส่วนสองชั้นหลัง (สีส้ม) มีไว้รู้ตัวและกู้คืน ถ้าทำแค่ห้าชั้นแรก วันที่ถูกเจาะสำเร็จจะไม่มีใครรู้และไม่มีแผนรับมือ

6. หลักการออกแบบด้านความปลอดภัย 8 ข้อ

เครื่องมือเปลี่ยนไปตามยุค แต่หลักคิดเบื้องหลังแทบไม่เปลี่ยน และเพราะโจทย์มักเล่าเป็นสถานการณ์ จึงควรเข้าใจความหมายมากกว่าจำชื่อ

หลักการความหมายตัวอย่าง
Least Privilegeให้สิทธิ์เท่าที่จำเป็น ถ้าโดนเจาะ ความเสียหายจำกัดอยู่แค่สิทธิ์นั้นrole ของแอปอ่านได้แค่ bucket เดียว
Defense in Depthป้องกันหลายชั้นที่แยกจากกันNACL + SG + IAM + เข้ารหัส + monitoring
Fail-Safe Defaultsค่าเริ่มต้นต้องเป็นการห้าม แล้วเปิดเฉพาะที่ระบุSG ปิดขาเข้าทั้งหมดตั้งแต่สร้าง
Separation of Dutiesไม่ให้ใครคนเดียวมีอำนาจครบทุกขั้นนักพัฒนา deploy (นำโค้ดขึ้นระบบจริง) ได้ แต่แก้สิทธิ์ต้องให้ทีม security อนุมัติ
Economy of Mechanismออกแบบให้เรียบง่าย ยิ่งซับซ้อนยิ่งมีช่องโหว่หนึ่ง SG ต่อหนึ่งชั้นของระบบ ตั้งชื่อให้รู้ทันทีว่าใช้กับอะไร
Complete Mediationตรวจสิทธิ์ทุกครั้งที่เข้าถึง ไม่จำผลครั้งก่อน สิทธิ์ที่ถอนจึงมีผลทันทีIAM ประเมิน policy ใหม่ทุกครั้งที่เรียก API
Open Designปลอดภัยแม้คนอื่นรู้วิธีออกแบบ ความลับอยู่ที่กุญแจ ไม่ใช่การปิดบังวิธีทำอัลกอริทึมเข้ารหัสเป็นมาตรฐานเปิด แต่กุญแจเป็นความลับ
Psychological Acceptabilityมาตรการต้องไม่ยุ่งยากจนคนหาทางเลี่ยงใช้ SSO แทนการให้จำรหัสห้าชุดจนคนจดรหัสแปะจอ

คู่ที่สับสนบ่อยคือ Least Privilege กับ Fail-Safe Defaults ข้อแรกพูดถึงปริมาณสิทธิ์ที่ให้ ข้อหลังพูดถึงจุดเริ่มต้น คืออะไรที่ไม่ได้ระบุไว้ให้ถือว่าห้ามก่อน ส่วน Open Design บอกว่าการซ่อนวิธีทำงานไม่ใช่ความปลอดภัยที่แท้จริง เพราะสักวันก็รั่วได้ ความปลอดภัยจึงต้องฝากไว้กับกุญแจ ซึ่งเปลี่ยนใหม่ได้ง่ายเมื่อหลุด

7. โยงกลับไปที่แล็บ iptables

สิ่งที่ทำในแล็บ Build VPC ตรงกับหลักการในช่วงนี้หลายข้อ การตั้ง policy ของ INPUT (ชุดกฎขาเข้า) เป็น DROP (ทิ้ง packet ที่ไม่ตรงกฎไหนเลย) คือ Fail-Safe Defaults กฎ ESTABLISHED,RELATED คือการจำการเชื่อมต่อแบบ stateful เหมือน SG การเปิดเฉพาะ port ที่จำเป็นและการสร้าง user ฐานข้อมูลที่มีสิทธิ์จำกัดคือ Least Privilege และการที่ทั้ง bastion (เครื่องตัวกลางที่ต้อง SSH ผ่านก่อนเข้าเครื่องอื่น) และ DB ต่างมีกฎของตัวเองกันไม่ให้ bastion ต่อ MySQL ได้ คือ Defense in Depth ขนาดย่อม

ถ้าเทียบ iptables กับ firewall สองชนิดของ AWS จะเห็นว่ามีลักษณะของทั้งสองปนกัน ด้านหนึ่งเหมือน SG คือติดกับตัวเครื่องและจำการเชื่อมต่อได้ อีกด้านเหมือน NACL คือเขียนกฎห้ามได้และตรวจตามลำดับโดยกฎแรกที่ตรงเป็นตัวตัดสิน

ทวนก่อนสอบ

โจทย์ของช่วงนี้ส่วนใหญ่ตอบได้ด้วยการไล่ทีละด่าน ถ้าถามว่า packet ผ่านไหม ให้ไล่ NACL ตามเลขจากน้อยไปมากจนเจอกฎแรกที่ตรง แล้วถามต่อว่าขากลับเปิด ephemeral port ไว้หรือยัง ส่วน SG ดูแค่กฎขาเข้า เพราะขากลับผ่านเอง ถ้าถามในมุม IAM ให้หา Deny ก่อนเสมอ เจอ Deny คือห้าม เจอแค่ Allow คืออนุญาต ไม่เจออะไรเลยก็ห้าม ส่วนโจทย์แบบสถานการณ์ ให้นึกว่าใครเป็นคนตั้งค่าสิ่งนั้น และหลักข้อไหนอธิบายได้ตรงที่สุด

กับดักของครึ่งหลังคือ Direct Connect เร็วและนิ่งกว่า VPN แต่ติดตั้งนานและไม่ได้เข้ารหัสให้เอง ระบบจริงจึงใช้ Direct Connect เป็นเส้นหลัก ใช้ VPN (อุโมงค์ IPsec ระหว่าง Customer Gateway กับ VGW) เป็นเส้นสำรอง และให้ BGP สลับเส้นให้อัตโนมัติ ใน Defense in Depth ห้าชั้นแรกมีไว้กัน ส่วน Monitoring กับ Incident มีไว้รู้ตัวและกู้คืน และ WAF ตามรายการเจ็ดชั้นอยู่ชั้น Resource

คู่หลักการที่ชอบหลอกคือ Least Privilege กับ Fail-Safe Defaults ถ้าโจทย์เล่าว่าให้สิทธิ์แค่ bucket เดียว นั่นคือ Least Privilege (ปริมาณสิทธิ์) แต่ถ้าเล่าว่าสร้าง SG ใหม่แล้วขาเข้าถูกปิดหมด นั่นคือ Fail-Safe Defaults (ค่าเริ่มต้นต้องเป็นการห้าม)
