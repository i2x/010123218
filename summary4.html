ช่วงนี้ต้องเข้าใจอะไร

มองช่วงนี้จากมุมของ Cloud Engineer ซึ่งไม่ได้สร้างโมเดล แต่ต้องทำให้ AI ทำงานในระบบจริงได้ในราคาที่รับไหว เรื่องจึงแบ่งเป็นสามก้อน ก้อนแรกคือโมเดลทำงานยังไงและคิดเงินยังไง (token, context, thinking token, cache) ซึ่งมีโจทย์คำนวณค่าใช้จ่าย ก้อนที่สองคือการต่อโมเดลเข้ากับระบบ (function calling, MCP, agent, RAG) ซึ่งต้องเข้าใจว่าใครทำอะไรและทำไม ก้อนที่สามคือโครงสร้างพื้นฐาน (GPU, VRAM, training กับ inference, quantization, self-host กับ API) ซึ่งมีโจทย์คำนวณหน่วยความจำและการเลือกทางที่คุ้มกว่า

1. ทำไม Cloud Engineer ต้องรู้เรื่อง AI

Cloud Engineer ไม่ได้เป็นคน train โมเดล (สอนโมเดลด้วยข้อมูลมหาศาล) แต่เป็นคนทำให้ AI ทำงานได้ใน production คือระบบจริงที่ลูกค้าใช้อยู่ เมื่อ AI มีปัญหา คนที่ต้องลงมือแก้คือทีมของบริษัทเอง ไม่ใช่บริษัทที่สร้างโมเดล

สไลด์จับคู่อาการเสียกับประเภทของปัญหาไว้ห้าแบบ ถ้าโมเดลตอบช้า มักเป็นเรื่องโครงสร้างพื้นฐาน เช่น GPU ไม่พอ (GPU หรือ Graphics Processing Unit คือชิปที่มีแกนประมวลผลเล็ก ๆ หลายพันแกนทำงานพร้อมกัน อธิบายในข้อ 10) ถ้า API ล่ม เป็นเรื่องของบริการหรือเครือข่าย (API หรือ Application Programming Interface คือช่องทางที่โปรแกรมใช้เรียกบริการ) ถ้าค่าใช้จ่ายพุ่ง เป็นงานลดต้นทุน ถ้าข้อมูลรั่ว เป็นเรื่องความปลอดภัย และถ้าคำตอบผิด มักแก้ที่ prompt ซึ่งคือข้อความที่ส่งให้โมเดล หรือแก้ที่ RAG ซึ่งคือการค้นเอกสารมาให้โมเดลอ่านก่อนตอบ (ข้อ 9)

2. LLM มาจากไหน

LLM (Large Language Model) คือโมเดลภาษาขนาดใหญ่ที่เรียนจากข้อความมหาศาลจนเขียนและตอบได้เหมือนคน วงการนี้เริ่มจากให้คนเขียนกฎเอง (ใช้ได้เฉพาะเมื่อข้อความตรงกฎ) ต่อมาให้เครื่องนับสถิติจากข้อมูลจริง แล้วจึงมาเป็นโครงข่ายประสาทเทียม (neural network) ซึ่งเป็นโมเดลที่เรียนรู้จากตัวอย่างด้วยการปรับตัวเลขจำนวนมากข้างใน โครงข่ายประสาทเทียมรุ่นแรกที่ใช้กับภาษา เช่น RNN (Recurrent Neural Network) และ LSTM (Long Short-Term Memory) อ่านข้อความทีละคำตามลำดับ จึงมีปัญหาสองข้อ คือลืมคำต้นประโยคเมื่อประโยคยาว และแบ่งงานให้คำนวณพร้อมกันไม่ได้

จุดเปลี่ยนคือ Transformer ซึ่งก็เป็นโครงข่ายประสาทเทียมเหมือนกัน แต่ใช้กลไก attention ให้ทุกคำในประโยคมองทุกคำอื่นได้พร้อมกัน จึงแก้ได้ทั้งสองปัญหา คือเข้าใจความสัมพันธ์ของคำที่อยู่ไกลกัน และคำนวณพร้อมกันบน GPU ได้ เมื่อรวมกับข้อมูลจำนวนมากและ GPU ที่แรงขึ้น LLM จึงเกิดขึ้น ต่อมายังพบว่ายิ่งเพิ่มขนาดโมเดล ข้อมูล และกำลังประมวลผล โมเดลก็ยิ่งเก่งขึ้นอย่างคาดการณ์ได้ (Scaling Laws)

บทเรียนจากการเทียบโมเดลแถวหน้าในสไลด์คือ ความฉลาดของแต่ละตัวห่างกันไม่มาก แต่ราคาต่างกันเป็นสิบเท่า โมเดลที่แพงที่สุดจึงไม่ใช่ตัวเลือกที่ดีที่สุดเสมอ ต้องเลือกให้เหมาะกับงาน

3. Token และ Context Window

LLM ทำงานเป็นสามขั้น ขั้นแรกคือ tokenization ซึ่งหั่นข้อความเป็นชิ้นเล็กเรียกว่า token แล้วแปลงเป็นเลข ขั้นที่สองส่งเลขเหล่านั้นเข้า Transformer เพื่อหาความน่าจะเป็นของ token ตัวถัดไป ขั้นสุดท้ายคือ decoding ซึ่งเลือก token มาหนึ่งตัว ต่อท้ายข้อความเดิม และวนกลับไปหาตัวถัดไปอีก โมเดลจึงสร้างคำตอบได้ทีละ token

token ไม่เท่ากับคำ เครื่องหมายวรรคตอนก็นับ และคำหนึ่งอาจถูกหั่นเป็นหลายชิ้น วิธีหั่นที่ใช้กันเรียกว่า BPE (Byte Pair Encoding) ซึ่งเริ่มจากตัวอักษรเดี่ยวแล้วรวมคู่ที่เจอบ่อยเข้าด้วยกันไปเรื่อย ๆ คำที่เจอบ่อยจึงเป็นชิ้นเดียว คำที่เจอน้อยแตกเป็นหลายชิ้น

token คือหน่วยที่ใช้คิดเงิน โดยแยกราคาขาเข้า (input) กับขาออก (output) และขาออกแพงกว่า เพราะขาเข้าคำนวณพร้อมกันได้ในรอบเดียว แต่ขาออกต้องสร้างทีละตัว สูตรคือ จำนวน token × ราคาต่อล้าน ÷ 1,000,000 แยกคิดขาเข้ากับขาออกแล้วรวมกัน เช่น โมเดลราคา $10 / $50 ต่อล้าน token คำขอที่ส่งเข้า 2,000 token และได้คำตอบ 500 token จะเสีย 2,000 × 10 ÷ 1,000,000 + 500 × 50 ÷ 1,000,000 = 0.02 + 0.025 = $0.045 ถ้ามีคนใช้วันละแสนครั้งก็เป็นวันละ $4,500

Context window คือจำนวน token สูงสุดที่โมเดลรับได้ในคำขอเดียว รวมขาเข้าและขาออก จุดสำคัญคือโมเดลไม่จำอะไรข้ามคำขอ แอปแชตที่ดูเหมือนจำได้คือแอปส่งประวัติการคุยทั้งหมดกลับเข้าไปทุกครั้ง context ที่ยาวขึ้นจึงทั้งแพงขึ้นและช้าลง สไลด์จึงแนะนำให้ใช้ RAG ดึงเฉพาะส่วนที่เกี่ยวข้อง แทนการยัดข้อมูลทั้งหมดลงใน prompt

4. Temperature และพารามิเตอร์ที่ใช้คุมคำตอบ

ในขั้น decoding โมเดลมีความน่าจะเป็นของ token ทุกตัว พารามิเตอร์เหล่านี้กำหนดว่าจะเลือกตัวไหน Temperature ค่า 0 เลือกตัวที่โอกาสสูงสุดเสมอ ถามซ้ำได้คำตอบเดิม เหมาะกับเขียนโค้ด ตอบข้อเท็จจริง และงานที่ต้องทำตามระเบียบ ค่ากลาง ๆ (ราว 0.7) เหมาะกับแชตทั่วไป ค่าสูง (1.0 ขึ้นไป) ทำให้ตัวที่โอกาสน้อยถูกเลือกบ่อยขึ้น เหมาะกับงานสร้างสรรค์

Top-p เรียง token จากโอกาสมากไปน้อย แล้วเก็บเฉพาะกลุ่มบนที่โอกาสรวมกันถึงค่า p ก่อนสุ่ม ค่าน้อยให้คำตอบแคบและแม่น ค่ามากให้คำตอบหลากหลาย Max tokens คือเพดานความยาวคำตอบ ใช้คุมค่าใช้จ่าย และ reasoning effort บอกโมเดลประเภทคิดก่อนตอบ (อธิบายในข้อ 5) ว่าให้คิดหนักแค่ไหน

5. Reasoning Model: โมเดลที่คิดก่อนตอบ

LLM แบบเดิมตอบทันที ส่วน reasoning model เขียนลำดับความคิด (chain-of-thought) ออกมาภายในก่อนแล้วจึงตอบ ผลลัพธ์ระหว่างทางกลายเป็นข้อมูลที่ใช้คิดขั้นถัดไป เหมือนคนที่จดเลขลงกระดาษทด แทนที่จะคิดในหัว ตัวอย่างในสไลด์คือเสื้อ $50 ลด 20% แล้วบวกภาษี 7% คำตอบที่ถูกคือ $50 × 0.80 = $40 แล้ว $40 × 1.07 = $42.80 ถ้าตอบทันทีมักผิดเพราะเอาเปอร์เซ็นต์มารวมกันก่อน

จุดที่ออกสอบคือ thinking token คิดเงินในราคา token ขาออก แม้ผู้ใช้จะมองไม่เห็นก็ตาม ถ้าโมเดลคิด 5,000 token ในราคาขาออก $50 ต่อล้าน ค่าความคิดอย่างเดียวคือ 5,000 × 50 ÷ 1,000,000 = $0.25 ซึ่งมักแพงกว่าตัวคำตอบหลายเท่า ผู้ให้บริการบางเจ้าจึงให้ตั้ง thinking budget คือเพดานจำนวน thinking token ต่อคำขอ ใช้คุมทั้งเวลาและค่าใช้จ่าย

สไลด์ยกตัวอย่างว่าคำขอแบบมีการคิดแพงกว่าแบบไม่คิด 578 เท่า ($0.2605 กับ $0.00045) แต่ตัวเลขนี้เอาโมเดลราคาถูกมาเทียบกับโมเดลราคาแพง จึงรวมผลของสองเรื่องไว้ด้วยกัน ถ้าเทียบในโมเดลเดียวกันที่ราคา $10 / $50 แบบไม่คิดจะเสีย 50 × 10 ÷ 1,000,000 + 200 × 50 ÷ 1,000,000 = $0.0105 แบบคิดเสีย $0.2605 ต่างกันราว 25 เท่า ซึ่งเป็นผลของ thinking token ล้วน ๆ

เพราะการคิดทั้งแพงและช้า ระบบที่ดีจึงแยกส่งตามความยาก (route by difficulty) งานง่ายอย่างแยกอีเมลสแปมหรือสรุปเอกสารใช้โมเดลทั่วไป งานปานกลางอย่างเขียน SQL (ภาษาที่ใช้สั่งฐานข้อมูล) ใช้การคิดระดับต่ำถึงกลาง งานที่ต้องไล่หลายขั้นอย่างหาสาเหตุบั๊กหรือออกแบบสถาปัตยกรรมใช้การคิดระดับสูง และงานพิสูจน์ทฤษฎีบทใช้ระดับสูงสุด (max)

6. Multimodal AI

Multimodal คือโมเดลที่รับข้อมูลได้หลายรูปแบบ ทั้งข้อความ ภาพ เสียง วิดีโอ และเอกสาร โมเดลแถวหน้าส่วนใหญ่เป็นแบบนี้แล้ว แต่ความสามารถไม่เท่ากัน บางตัวรับภาพได้แต่สร้างภาพไม่ได้ จึงต้องแยกดูว่ารับเข้าได้อะไรและสร้างออกได้อะไร เวลาเรียกผ่าน API ข้อความหนึ่งชิ้นอาจมีหลายส่วนปนกัน เช่น ส่วนหนึ่งเป็นคำสั่ง อีกส่วนเป็นภาพ สิ่งที่ Cloud Engineer ต้องคิดคือภาพและเสียงมีขนาดใหญ่กว่าข้อความมาก จึงกินทั้ง bandwidth (ปริมาณข้อมูลที่ส่งผ่านเครือข่ายได้ต่อวินาที) พื้นที่ใน context และค่าใช้จ่ายมากกว่า

7. เรียกใช้ LLM ผ่าน API

ผู้ให้บริการ LLM แต่ละเจ้าเด่นคนละด้าน สำหรับองค์กร บริการ AI ของผู้ให้บริการ Cloud อย่าง AWS และ Azure มักเหมาะกว่า เพราะใช้ IAM (Identity and Access Management ระบบจัดการตัวตนและสิทธิ์ ช่วงที่ 3), VPC และมาตรฐานความปลอดภัยที่บริษัทมีอยู่แล้วได้ เกือบทุกเจ้ารองรับรูปแบบคำขอแบบเดียวกับ OpenAI (OpenAI-compatible) การย้ายเจ้าจึงเปลี่ยนแค่ที่อยู่ของ API กับ key ไม่ต้องเขียนโค้ดใหม่ ช่วยลดการผูกติดกับเจ้าเดียว (vendor lock-in) และทำระบบสำรองได้ง่ายเมื่อเจ้าหลักล่ม

POST /v1/chat/completions
Authorization: Bearer $API_KEY
{
  "model": "...",
  "messages": [
    {"role": "system", "content": "You are a cloud computing expert."},
    {"role": "user",   "content": "Explain VPC in 3 sentences."}
  ],
  "temperature": 0.7
}

คำขอหนึ่งครั้งเป็น HTTP POST ที่แนบ API key มาใน header และส่ง JSON ที่มีชื่อโมเดล พารามิเตอร์ และรายการข้อความ ข้อความแต่ละชิ้นมี role บอกว่าใครพูด system คือคำสั่งตั้งต้นที่กำหนดบทบาทของโมเดล user คือข้อความของผู้ใช้ และ assistant คือคำตอบเก่าของโมเดล ที่ต้องส่งคำตอบเก่ากลับเข้าไปทุกครั้งเมื่อคุยหลายรอบ ก็เพราะ API แบบนี้เป็น stateless คือไม่จำอะไรระหว่างคำขอเลย ส่วน key ห้ามฝังไว้ในโค้ดเพราะโค้ดอาจหลุด ให้เก็บในตัวแปรสภาพแวดล้อม (ค่าที่ตั้งไว้ในระบบ แยกจากตัวโค้ด) หรือในบริการเก็บรหัสลับแทน

อีกเรื่องที่ช่วยลดค่าใช้จ่ายได้มากคือ prompt cache ทุกครั้งที่โมเดลอ่านข้อความ โมเดลต้องคำนวณค่ากลางของ token ทุกตัวเก็บไว้ (เรียกว่า KV cache) ถ้าข้อความส่วนต้นของคำขอเหมือนคำขอก่อนหน้าทุกตัวอักษร ค่ากลางของส่วนนั้นก็เหมือนเดิม ผู้ให้บริการจึงหยิบมาใช้ซ้ำได้โดยไม่ต้องคำนวณใหม่ และคิดราคาส่วนนั้นถูกลงราวสิบเท่า แต่ถ้าเปลี่ยนแม้คำเดียว cache จะใช้ไม่ได้ตั้งแต่จุดที่เปลี่ยนเป็นต้นไป ระบบจึงควรวางส่วนที่ไม่เปลี่ยนไว้ต้นข้อความ เช่น system prompt และคู่มือที่แนบทุกครั้ง แล้ววางคำถามที่เปลี่ยนไว้ท้าย ตัวชี้วัดสำคัญใน production จึงเป็น KV-cache hit rate คือสัดส่วนของ token ที่ใช้ cache ได้

8. Function Calling, MCP และ AI Agent

แนวคิดเรื่องการใช้โมเดลพัฒนามาเป็นสามชั้นที่ซ้อนกัน ไม่ได้มาแทนกัน ชั้นในสุดคือ Prompt Engineering (ควรพูดกับโมเดลว่าอะไร) ครอบด้วย Context Engineering (ควรให้ข้อมูลอะไรกับโมเดล) และชั้นนอกสุดคือ Harness Engineering (ควรสร้างระบบอะไรรอบโมเดล) prompt engineering จึงยังสำคัญอยู่ เพียงแต่เป็นแค่ส่วนหนึ่งของระบบที่ใหญ่กว่า สไลด์ใช้สูตร Agent = Model + Harness โมเดลเหมือน CPU ที่คิดและตัดสินใจ context เหมือน RAM คือพื้นที่ทำงานที่โมเดลมองเห็นในขณะนั้น ส่วน harness คือระบบที่ครอบโมเดลไว้ ได้แก่การคุมรอบการทำงาน เครื่องมือและสิทธิ์ การจัดการความจำ การรับมือข้อผิดพลาด และการตรวจผล

Function calling (tool use) ให้โมเดลใช้ API จริงได้ เราบอกโมเดลล่วงหน้าว่ามีเครื่องมืออะไร แต่ละตัวมีชื่อ คำอธิบาย (โมเดลอ่านช่องนี้เพื่อตัดสินว่าจะใช้เมื่อไร) และพารามิเตอร์ จุดที่ต้องเข้าใจคือโมเดลไม่ได้เรียก API เอง โมเดลแค่ตอบกลับมาว่าอยากให้เรียกฟังก์ชันไหนด้วยค่าอะไร แอปของเราเป็นคนเรียกจริงแล้วส่งผลกลับให้โมเดลเขียนคำตอบ สิทธิ์จึงอยู่ที่แอป และต้องให้น้อยที่สุดตามหลัก least privilege ในช่วงที่ 3

MCP (Model Context Protocol) คือมาตรฐานเปิดสำหรับต่อ AI กับเครื่องมือและข้อมูล เปรียบว่าเป็น "USB-C ของ AI" ถ้าไม่มีมาตรฐานกลาง แอป AI M ตัวกับเครื่องมือ N ตัวต้องเขียนตัวเชื่อม M × N ชุด แต่ถ้าใช้ MCP เครื่องมือเขียนเป็น MCP server ครั้งเดียว แอปรองรับ MCP ครั้งเดียว รวมเป็น M + N ชุด เช่น 3 แอปกับ 4 เครื่องมือ จาก 12 ชุดเหลือ 7 ชุด และใช้กับโมเดลของเจ้าไหนก็ได้ สไลด์แนะนำ function calling สำหรับงานง่าย และ MCP สำหรับการเชื่อมต่อระดับ production

AI agent ประกอบด้วย LLM ที่เป็นสมอง เครื่องมือที่เป็นมือ และความจำซึ่งก็คือ context ทำงานเป็นวงจรสี่ขั้น Plan วิเคราะห์งานและเลือกวิธี Act เรียกเครื่องมือทีละขั้น Verify ตรวจผลและแก้เองถ้าผิด และ Loop ตัดสินว่าจะลองใหม่ ส่งต่อให้คน หรือจบงาน ต่างจากแชตบอตที่ถามครั้งเดียวตอบครั้งเดียว agent ที่ใช้กันอยู่แบ่งได้สี่แบบตามงาน คือ coding agent ที่เขียน แก้ และรีวิวโค้ด chat agent ที่ถามตอบ วิเคราะห์ และช่วยเขียน workflow agent ที่ทำขั้นตอนงานธุรกิจให้อัตโนมัติ และ computer-use agent ที่ควบคุมหน้าจอและท่องเว็บแทนคน

เมื่อใช้หลาย agent ร่วมกัน (multi-agent) มีสามรูปแบบ Orchestrator-Worker มีหัวหน้าแตกงานแล้วแจกให้ลูกทีมทำพร้อมกัน Pipeline ส่งงานต่อกันเป็นทอด เช่น เขียนโค้ด ส่งรีวิว แล้วส่งทดสอบ และ Debate ให้ตัวหนึ่งเสนอ อีกตัวหาจุดอ่อนมาแย้ง ส่วนหน้าที่ของ Cloud Engineer คือ deploy (นำขึ้นระบบจริง) และดูแลโครงสร้างพื้นฐานที่ agent ทำงานอยู่ ไม่ใช่สร้าง agent เอง

9. Embedding, Vector Database และ RAG

LLM รู้แค่สิ่งที่อยู่ใน context และไม่เคยเห็นเอกสารภายในของบริษัท ส่วนการค้นแบบจับคำตรงกันก็หาข้อความที่ความหมายเหมือนแต่เขียนต่างกันไม่เจอ เช่น "ไม่สบายหยุดงาน" กับ "sick leave" จึงต้องค้นด้วยความหมาย

Embedding คือการแปลงข้อความเป็น vector (รายการตัวเลขหลายร้อยตัวขึ้นไป) ด้วยโมเดลที่ฝึกมาให้ข้อความที่ความหมายคล้ายกันได้ vector ใกล้กัน แม้จะต่างภาษา ความใกล้วัดด้วย cosine similarity = (A · B) / (|A| × |B|) โดย A · B คือผลรวมของผลคูณตัวเลขตำแหน่งเดียวกัน และ |A| คือความยาวของ vector (รากที่สองของผลรวมกำลังสอง) ค่านี้ดูแค่มุมระหว่าง vector ไม่สนความยาว ค่า 1 คือทิศเดียวกัน 0 คือไม่เกี่ยวกัน เช่น A = [1, 2] กับ B = [2, 4] ได้ (1×2 + 2×4) ÷ (√(1²+2²) × √(2²+4²)) = 10 ÷ (√5 × √20) = 10 ÷ √100 = 10 ÷ 10 = 1 เพราะ B คือ A ที่ยาวขึ้นสองเท่า ชี้ไปทางเดียวกัน

Vector database เก็บ vector และค้นหารายการที่คล้ายที่สุด (similarity search) ต่างจากฐานข้อมูลแบบเดิมที่ค้นแบบตรงเป๊ะ

RAG (Retrieval-Augmented Generation) มีสามขั้น Retrieve ค้นเอกสารที่เกี่ยวข้องจาก vector database Augment ใส่เอกสารนั้นลงใน prompt คู่กับคำถาม และ Generate ให้โมเดลตอบจากเอกสาร ไม่ใช่จากความจำ ผลคือลด hallucination (โมเดลแต่งข้อมูลที่ไม่มีจริง) บอกแหล่งที่มาได้ และอัปเดตความรู้ได้ด้วยการอัปเดตเอกสาร โดยไม่ต้อง train โมเดลใหม่

ขั้นตอนเต็มแบ่งเป็นสองช่วง ช่วงเตรียมเอกสารทำล่วงหน้า คือโหลดเอกสาร (Ingest) หั่นเป็นชิ้น (Chunk) แปลงเป็น vector (Embed) แล้วเก็บลง vector database (Store) ขนาดชิ้นต้องพอดี ใหญ่เกินไปความหมายจะปนกัน เล็กเกินไปจะขาดบริบท ช่วงตอบคำถามทำทุกครั้งที่มีคนถาม คือแปลงคำถามเป็น vector ค้นหาชิ้นที่ใกล้ที่สุด แล้วให้ LLM เขียนคำตอบ กับดักคือทั้งสองช่วงต้องใช้ embedding model ตัวเดียวกัน ไม่อย่างนั้น vector จะเทียบกันไม่ได้

10. งาน AI ต่างจากงานเว็บ และทำไมต้องใช้ GPU

งานเว็บใช้ CPU เป็นหลัก เป็น stateless (เครื่องไม่ต้องจำอะไรไว้ เครื่องไหนรับคำขอก็ได้) ย้ายข้อมูลน้อย และขยายด้วยการเพิ่มเครื่อง ส่วนงาน AI ใช้ GPU เป็นหลัก เป็น stateful (ต้องโหลดโมเดลขนาดใหญ่ไว้ในหน่วยความจำ) ย้ายข้อมูลมหาศาล เน้น throughput (ปริมาณงานที่ทำเสร็จต่อหน่วยเวลา ต่างจาก latency ซึ่งคือเวลาที่รอตั้งแต่ส่งคำขอจนได้คำตอบ) และขยายด้วยการเพิ่ม GPU พร้อมเครือข่ายระหว่าง GPU

การคำนวณของ LLM แทบทั้งหมดคือการคูณเมทริกซ์ (ตารางตัวเลขขนาดใหญ่) ซึ่งแตกเป็นการคูณบวกเล็ก ๆ จำนวนมากที่ทำพร้อมกันได้ GPU มีแกนเล็กจำนวนมหาศาลจึงเหมาะกว่า CPU ที่มีแกนเก่งแต่น้อย แกนทั่วไปของ GPU เรียกว่า CUDA core ใช้คำนวณแบบขนานทั่วไป ส่วน GPU รุ่นใหม่ยังมี Tensor core ซึ่งเป็นแกนที่ทำมาเพื่อคูณเมทริกซ์โดยเฉพาะ และใช้หน่วยความจำแบบ HBM (High Bandwidth Memory) ที่ส่งข้อมูลให้แกนได้เร็วมาก เพราะแกนจำนวนมากจะไร้ประโยชน์ถ้าป้อนข้อมูลไม่ทัน

หน่วยความจำของ GPU (VRAM) คือข้อจำกัดหลักของขนาดโมเดล คำนวณคร่าว ๆ ได้จาก จำนวน parameter × byte ต่อ parameter โดย parameter คือตัวเลขแต่ละตัวที่โมเดลเรียนรู้มา (B = พันล้าน) ถ้าเก็บแบบ FP16 (floating point 16 บิต เลขทศนิยมขนาด 16 บิต) แต่ละตัวจะใช้ 2 byte (1 byte = 8 บิต) โมเดล 70B จึงใช้ 70 × 2 = 140 GB และโมเดล 405B ใช้ 810 GB เกินความจุของ GPU ตัวเดียวหลายเท่า ต้องแบ่งไปหลาย GPU และหลายเครื่อง

เมื่อต้องใช้หลาย GPU ความเร็วของสายที่ต่อระหว่างกันจึงสำคัญ GPU ในเครื่องเดียวกันต่อกันด้วย NVLink ซึ่งเร็วมาก โดยมี NVSwitch เป็นตัวสลับกลางที่ทำให้ GPU ทุกตัวในเครื่องคุยกันผ่าน NVLink ได้พร้อมกัน ส่วน GPU ต่างเครื่องต่อกันด้วย InfiniBand ซึ่งช้ากว่าหลายเท่า ระวังหน่วยตอนเทียบ InfiniBand บอกความเร็วเป็น Gb/s (bit) ต้องหารด้วย 8 ก่อนจึงเทียบกับ GB/s (byte) ได้ หลักที่ได้คืองานที่ต้องคุยกันถี่ควรอยู่ในเครื่องเดียวกัน

11. Training กับ Inference และ Quantization

Training คือการสอนโมเดลจากข้อมูลมหาศาลจนได้ไฟล์ weights (ค่าของ parameter ทั้งหมดที่โมเดลเรียนรู้มา) ส่วน inference คือการใช้โมเดลที่สอนเสร็จแล้วตอบคำถาม ทุกครั้งที่เรียก API ก็คือ inference สองงานนี้ต้องการโครงสร้างพื้นฐานต่างกันมาก

เครือข่ายระหว่าง GPUไม่จำเป็นสำคัญมาก

ตารางนี้ไม่ต้องท่อง เพราะทุกแถวไล่เหตุผลได้ training ต้องเก็บ gradient (ตัวเลขที่บอกว่า weight แต่ละตัวควรปรับเท่าไร) และสถานะของ optimizer (อัลกอริทึมที่ใช้ gradient ไปปรับ weights) เพิ่ม จึงใช้หน่วยความจำหลายเท่า ต้องใช้ตัวเลขละเอียดเพราะการปรับแต่ละครั้งเล็กมาก ถ้าตัวเลขหยาบไปจะถูกปัดทิ้ง ต้องใช้เครือข่ายเร็วเพราะ GPU ทุกตัวต้องแลก gradient กันทุกรอบ และต้องมี checkpoint (บันทึกสถานะเป็นระยะ) เพราะเมื่อใช้ GPU หลายพันตัวนานหลายสัปดาห์ แทบแน่นอนว่าจะมีเครื่องพังระหว่างทาง จะได้ไม่ต้องเริ่มใหม่จากศูนย์

Quantization คือการเก็บ weights ด้วยจำนวน bit ที่น้อยลง ใช้กับ inference โมเดล 70B ที่ FP16 (2 byte) ใช้ 140 GB ถ้าลดเป็น INT8 (เลขจำนวนเต็ม 8 บิต = 1 byte) เหลือ 70 GB และถ้าลดเป็น INT4 (4 บิต = ครึ่ง byte) เหลือ 35 GB คุณภาพลดลงเพียงเล็กน้อย แต่ได้ทั้งใช้ GPU น้อยลงและตอบเร็วขึ้น ที่เร็วขึ้นเพราะทุก token ที่สร้างต้องอ่าน weights ทั้งหมดผ่านหน่วยความจำ ตัวเลขยิ่งเล็ก ข้อมูลที่ต้องอ่านก็ยิ่งน้อย

12. รันโมเดลเองหรือใช้ API

การใช้ API เริ่มได้ทันที ไม่ต้องดูแลฮาร์ดแวร์ ได้โมเดลรุ่นล่าสุด และขยายรับปริมาณงานได้เอง แต่ค่า token สะสมจนแพง ข้อมูลต้องออกนอกเครือข่ายของเรา มีเพดานจำนวนคำขอ (rate limit) และผู้ให้บริการเปลี่ยนราคาได้ ส่วนการรันเอง (self-host) ข้อมูลไม่ออกนอกองค์กร ไม่มีค่า token ทำ fine-tuning ได้ (สอนโมเดลต่อด้วยข้อมูลของเราให้เก่งงานเฉพาะทาง ต่างจาก RAG ที่ไม่แตะตัวโมเดล) และไม่ผูกกับผู้ให้บริการ แต่ต้องลงทุนฮาร์ดแวร์ ดูแลเอง โมเดลอาจตามหลังรุ่นแถวหน้า และต้องมีคนเชี่ยวชาญ

สรุปเป็นหลักเลือกได้ว่า ควรเลือก self-host เมื่อข้อมูลห้ามออกนอกองค์กร ปริมาณใช้งานสูงมากและสม่ำเสมอ ต้อง fine-tune ต้องการงบที่คาดการณ์ได้ ต้องการ latency ต่ำมากเพราะไม่ต้องส่งคำขอออกไปนอกเครือข่าย หรือต้องทำตาม compliance คือกฎระเบียบที่บังคับให้ข้อมูลต้องอยู่ในที่ของเราเอง ควรเลือก API เมื่อต้องการเริ่มเร็ว ปริมาณน้อยหรือขึ้นลงไม่แน่นอน ทีมไม่มีคนเชี่ยวชาญ หรือต้องการโมเดลล่าสุด

เหตุผลเบื้องหลังคือรูปแบบของค่าใช้จ่าย ค่า API เป็นค่าใช้จ่ายผันแปร ใช้มากจ่ายมาก ส่วน self-host เป็นค่าใช้จ่ายเกือบคงที่สำหรับจำนวน GPU ที่เช่าไว้ เพราะต้องจ่ายค่า GPU ทุกชั่วโมงไม่ว่าจะมีคนใช้หรือไม่ และเพิ่มเป็นขั้นเมื่อปริมาณงานโตจนต้องเช่า GPU เพิ่ม ซึ่งยังโตช้ากว่าค่า API มาก ตอนปริมาณน้อย API จึงถูกกว่ามาก แต่เมื่อปริมาณเพิ่มขึ้นถึงจุดหนึ่ง เส้นทั้งสองจะตัดกัน (จุดคุ้มทุน) และหลังจากนั้น self-host ถูกกว่า

ตัวเลขจุดคุ้มทุนในสไลด์ไม่ตรงกันเอง กฎสั้น ๆ บอกราว 10M (สิบล้าน) token ต่อวัน แต่ตารางแสดงที่ราว 100M token ต่อวัน ถ้าโจทย์ให้ตัวเลขมา ให้ตอบตามที่โจทย์อ้าง สิ่งที่ต้องเข้าใจจริงคือเหตุผลว่าทำไมปริมาณสูงจึงคุ้มกับ self-host

13. Managed AI และชิป AI ของผู้ให้บริการ Cloud

ทางเลือกตรงกลางระหว่างใช้ API กับซื้อเครื่องเอง คือเช่า GPU ผ่านบริการที่ดูแลเครื่องให้ (managed service ของ AWS หรือ Google) ได้ควบคุมโมเดลเองโดยไม่ต้องซื้อฮาร์ดแวร์ ผู้ให้บริการบางรายเน้น spot instance คือเครื่องที่ปล่อยเช่าจากกำลังที่ว่างอยู่ ราคาถูกแต่ถูกเรียกคืนได้ทุกเมื่อ จึงเหมาะกับงานที่หยุดแล้วทำต่อจาก checkpoint ได้ เช่น training

ผู้ให้บริการ Cloud ยังออกแบบชิป AI ของตัวเอง เช่น AWS มี Trainium สำหรับ training และ Inferentia สำหรับ inference (จำจากชื่อได้เลย) ส่วน Google มี TPU (Tensor Processing Unit) ที่ใช้ได้ทั้ง training และ inference ชิปเหล่านี้มักถูกกว่า GPU เพราะออกแบบมาทำเฉพาะงาน AI แต่ใช้ได้แค่บน Cloud ของเจ้านั้น และอาจต้องปรับโค้ดให้เข้ากัน ซึ่งก็คือการแลกราคากับการผูกติดผู้ให้บริการ

14. แผนผังเลือกบริการ

แชตหรือถามตอบทั่วไปใช้ LLM API ถ้าต้องใช้ข้อมูลภายในให้เพิ่ม RAG งานที่เป็นขั้นตอนอัตโนมัติใช้ agent ร่วมกับ MCP การ train โมเดลเองใช้ managed service และเพิ่มกลุ่ม GPU ที่ต่อกันด้วยเครือข่ายเร็วเมื่องานใหญ่ inference ที่ต้องเร็วและถูกใช้ชิปเฉพาะทางหรือโมเดลที่ผ่าน quantization และถ้าต้องการ latency ต่ำที่สุด ให้รันที่ edge ซึ่งอยู่ใกล้ผู้ใช้มากที่สุด เช่น จุดให้บริการของ Cloud ใกล้ผู้ใช้ ในเครือข่ายมือถือ 5G หรือบนตัวอุปกรณ์เลย

ทวนก่อนสอบ

โจทย์คำนวณของช่วงนี้มีไม่กี่แบบ ค่าใช้จ่ายคือ token × ราคาต่อล้าน ÷ ล้าน แยกขาเข้ากับขาออกแล้วรวมกัน โดย thinking token คิดราคาขาออกเสมอ หน่วยความจำคือ parameter × byte ต่อ parameter (FP16 = 2, INT8 = 1, INT4 = 0.5) และ training ใช้หลายเท่าของนั้น MCP เปลี่ยนจำนวนตัวเชื่อมจาก M × N เป็น M + N ส่วน cosine similarity ดูแค่มุมระหว่าง vector ถ้าเทียบ NVLink กับ InfiniBand ให้แปลง Gb/s เป็น GB/s ก่อน (หารด้วย 8) และจุดคุ้มทุนของ self-host ให้ตอบตามตัวเลขที่โจทย์ใช้

โจทย์แนวคิดให้จำว่าโมเดลไม่จำอะไรข้ามคำขอ และไม่ได้เรียก API เอง แอปเป็นคนเรียก RAG ลด hallucination ได้โดยไม่ต้อง train ใหม่ แต่ทั้งสองช่วงของ RAG ต้องใช้ embedding model ตัวเดียวกัน prompt cache ได้ผลเมื่อวางส่วนที่ไม่เปลี่ยนไว้ต้นข้อความ และ self-host คุ้มเมื่อปริมาณสูงเพราะต้นทุนเกือบคงที่ ส่วน API คุ้มเมื่อปริมาณน้อยเพราะจ่ายตามที่ใช้
