ช่วงนี้ต้องเข้าใจอะไร

แกนของช่วงนี้คือคำถามเดียว ว่า packet ตัวหนึ่งเดินจากอินเทอร์เน็ตไปถึงฐานข้อมูลใน VPC ได้ยังไง และอะไรเป็นตัวกำหนดว่าเดินได้หรือไม่ได้ ต้องคำนวณขนาดช่วง IP แบบ CIDR ได้ เข้าใจว่า subnet เป็น public หรือ private เพราะ route table อย่างเดียว เข้าใจว่า Internet Gateway กับ NAT Gateway ต่างกันที่ทิศทาง และวางของสำคัญไว้ลึกที่สุดแบบ three-tier ส่วน SDN กับ NFV คือเบื้องหลังที่ทำให้ Cloud สร้างเครือข่ายด้วยซอฟต์แวร์ได้ แล็บทั้งสามเอาแนวคิดเหล่านี้มาลงมือจริง โดยแล็บ WebApp เพิ่มเรื่อง REST API กับ CORS (ข้อ 12) ซึ่งต้องเข้าใจว่าใครเป็นคนบังคับใช้กฎ และสิ่งที่ต้องจำจากแล็บคือเหตุผลของแต่ละขั้น ไม่ใช่คำสั่ง

1. VPC คืออะไร

VPC (Virtual Private Cloud) คือเครือข่ายส่วนตัวที่กันแยกไว้ให้เราบน Cloud การแยกนี้ทำด้วยซอฟต์แวร์ อุปกรณ์จริงยังใช้ร่วมกับลูกค้ารายอื่นอยู่ (ลูกค้าแต่ละรายเรียกว่า tenant แปลว่าผู้เช่า) แต่ข้อมูลข้ามจาก VPC หนึ่งไปอีก VPC เองไม่ได้ เหมือนได้ data center ส่วนตัวมาหนึ่งแห่งที่ออกแบบผังเครือข่ายได้เอง

ใน VPC เราเลือกช่วง IP เองได้ และแบ่งเป็นเครือข่ายย่อยที่เรียกว่า subnet ได้ เรากำหนดได้ด้วยว่า traffic แบบไหนออกอินเทอร์เน็ตได้ (traffic คือข้อมูลที่วิ่งอยู่ในเครือข่าย) และยังมี firewall (ตัวกรองว่า traffic ไหนผ่านได้) ให้สองชั้น คือ Security Group (SG) กับ NACL (Network Access Control List) ซึ่งจะเรียนในช่วงที่ 3 ชื่อเรียกต่างกันไปตามผู้ให้บริการ AWS เรียกว่า VPC ส่วน Azure เรียกว่า VNet

2. การเขียนช่วง IP แบบ CIDR

CIDR (Classless Inter-Domain Routing) คือวิธีเขียนช่วง IP ที่ใช้กันในปัจจุบัน แต่ก่อนจะอ่าน CIDR ได้ต้องรู้จัก บิต ก่อน คอมพิวเตอร์เก็บตัวเลขเป็นเลขฐานสอง ซึ่งแต่ละหลักมีค่าได้แค่ 0 หรือ 1 หลักหนึ่งหลักนี้เรียกว่าหนึ่งบิต ถ้ามี 1 บิตจะเขียนได้ 2 แบบ (0, 1) ถ้ามี 2 บิตได้ 4 แบบ (00, 01, 10, 11) ถ้ามี 3 บิตได้ 8 แบบ ทุกครั้งที่เพิ่มหนึ่งบิต จำนวนแบบจะคูณสอง ดังนั้น n บิตเขียนได้ 2n แบบ ประโยคนี้คือที่มาของสูตรทั้งหมดในหัวข้อนี้

IPv4 หนึ่งตัวยาว 32 บิต เขียนเป็นเลขสี่ชุดคั่นด้วยจุด ชุดละ 8 บิต แต่ละชุดจึงมีค่าได้ 28 = 256 แบบ คือ 0 ถึง 255 ช่วง IP เขียนแบบ CIDR เช่น 10.0.0.0/16 ตัวเลขหลัง / เรียกว่า prefix บอกว่าบิตทางซ้ายกี่บิตถูกล็อกไว้เป็นส่วนของเครือข่าย ซึ่งทุกเครื่องในช่วงต้องมีเหมือนกัน บิตที่เหลือทางขวาเอาไปแจกเป็นเลขประจำเครื่อง /16 จึงล็อกสองชุดแรก (8 + 8 = 16 บิต) ไว้ที่ 10.0 และเหลือ 32 − 16 = 16 บิตให้แจก ได้ 216 = 65,536 IP ตั้งแต่ 10.0.0.0 ถึง 10.0.255.255 เหมือนเบอร์โทรที่ล็อกรหัสพื้นที่ไว้ ส่วนเลขที่เหลือเอาไปแจกให้แต่ละบ้าน

สูตรที่ต้องใช้ให้เป็นคือ จำนวน IP = 2(32 − prefix) ตัวเลขหลัง / ยิ่งมาก IP ยิ่งน้อย วิธีคิดเร็วในห้องสอบคือจำไว้ตัวเดียวว่า /24 มี 256 ตัว (ชุดสุดท้ายว่างให้แจกทั้งชุด) แล้วนับจากตรงนั้น prefix มากขึ้นหนึ่งก็หารสอง (/25 มี 128 ตัว /26 มี 64 ตัว) น้อยลงหนึ่งก็คูณสอง เวลาแบ่งช่วงใหญ่เป็นช่วงย่อย เลขเริ่มของแต่ละช่วงต้องเป็นพหุคูณของขนาดช่วง เช่น แบ่ง 10.0.1.0/24 เป็น /25 สองก้อนจะได้ .0–.127 กับ .128–.255 จะเริ่มที่ .100 ไม่ได้ เพราะ 100 ไม่ใช่พหุคูณของ 128

บน AWS ต้องหักออกอีก 5 IP ในทุก subnet คือสี่ตัวแรกกับตัวสุดท้าย เพราะ AWS กันไว้ใช้เอง (เช่น router และ DNS ของ VPC) ระวังอย่าสับสนกับเครือข่ายทั่วไปที่หักแค่ 2 ตัว คือ network address (เลขตัวแรก ใช้เรียกทั้งช่วง) กับ broadcast (เลขตัวสุดท้าย ใช้ส่งถึงทุกเครื่องในช่วงพร้อมกัน)

ตัวอย่างโจทย์ ถ้าต้องวางเครื่อง 100 เครื่องใน subnet เดียวบน AWS ให้ไล่ดู /25 ใช้ได้ 128 − 5 = 123 ตัวซึ่งพอ แต่ /26 ใช้ได้ 64 − 5 = 59 ตัวไม่พอ คำตอบคือ /25

3. ช่วง Private IP ตาม RFC 1918

มาตรฐาน RFC 1918 (เอกสารมาตรฐานของอินเทอร์เน็ตชุด Request for Comments ฉบับที่ 1918) กันช่วง IP ไว้สามช่วงให้ใช้เป็น private IP ใครจะใช้ซ้ำกันก็ได้ เพราะ router บนอินเทอร์เน็ตตกลงกันว่าจะไม่ส่งต่อ packet ที่ไปหาช่วงเหล่านี้ VPC จึงควรใช้ IP จากสามช่วงนี้ ถ้าไปใช้ช่วงที่เป็น IP จริงบนอินเทอร์เน็ต เครื่องใน VPC จะคุยกับเครื่องจริงที่ใช้ IP นั้นไม่ได้ เพราะ route table (ตารางบอกทาง อธิบายในข้อ 5) จะเข้าใจว่าปลายทางอยู่ใน VPC เอง

ช่วงครอบคลุม
10.0.0.0/810.0.0.0 ถึง 10.255.255.255
172.16.0.0/12172.16.0.0 ถึง 172.31.255.255
192.168.0.0/16192.168.0.0 ถึง 192.168.255.255

กับดักที่เจอบ่อยคือช่วง 172.16.0.0/12 ซึ่งคิดออกได้จากหลักเดิม /12 ล็อกชุดแรกไว้ 8 บิตที่ 172 แล้วล็อกต่ออีก 4 บิตทางซ้ายของชุดที่สอง ชุดที่สองจึงเหลือ 4 บิตทางขวาให้เปลี่ยนได้ 24 = 16 ค่า เริ่มจาก 16 ไปจนถึง 16 + 15 = 31 ช่วงนี้จึงครอบคลุมแค่ 172.16 ถึง 172.31 ดังนั้น 172.32.1.1 ไม่ใช่ private IP แม้จะขึ้นต้นด้วย 172

4. Public subnet และ Private subnet

Public subnet มีเส้นทางออกไปยัง Internet Gateway เครื่องข้างในมี public IP ได้และคนข้างนอกเข้าถึงได้ ใช้วางของที่ต้องหันหน้าออกอินเทอร์เน็ต เช่น load balancer (ตัวกระจายคำขอไปหลาย server) และ bastion (เครื่องที่เป็นประตูให้ผู้ดูแลเข้าเครือข่าย) Private subnet ไม่มีเส้นทางไป Internet Gateway คนข้างนอกจึงเข้าไม่ถึง ใช้วางของสำคัญอย่าง app server (เครื่องที่รันโปรแกรมประมวลผลของแอป) และฐานข้อมูล

ประโยคที่ต้องจำให้ขึ้นใจคือ public กับ private ต่างกันที่ route table เท่านั้น subnet ไม่ได้มีป้ายติดมาตั้งแต่สร้าง แต่กลายเป็น public ทันทีที่ route table มีเส้นทาง 0.0.0.0/0 ไปที่ Internet Gateway

หลักออกแบบมีสามข้อ กระจาย subnet ไปหลาย AZ ให้ public subnet เล็กและ private subnet ใหญ่เพราะของส่วนใหญ่อยู่ข้างใน และถ้าวันหน้าจะเชื่อม VPC สองก้อนเข้าหากัน (VPC peering) ช่วง IP ต้องไม่ทับกัน ไม่อย่างนั้นระบบจะไม่รู้ว่า IP นั้นหมายถึงเครื่องฝั่งไหน

5. Route Table

Route table คือตารางกฎที่บอกว่า packet ที่จะไปปลายทางไหนให้ส่งไปทางใด แต่ละกฎมี Destination (ช่วง IP ปลายทาง) กับ Target (ส่งไปที่ใด) ใน VPC ทั่วไปจะเจอกฎสามแบบ

กฎความหมายอยู่ที่ไหน
10.0.0.0/16 → localปลายทางอยู่ใน VPC เดียวกัน ส่งกันภายในทุก route table (มีให้อัตโนมัติ) เครื่องใน VPC เดียวกันจึงคุยกันได้ทันที
0.0.0.0/0 → igwปลายทางอื่นทั้งหมด ออกทาง Internet Gatewaypublic subnet
0.0.0.0/0 → natปลายทางอื่นทั้งหมด ส่งไป NAT Gatewayprivate subnet

0.0.0.0/0 ไม่ล็อกบิตไหนเลยจึงครอบคลุมทุก IP เรียกว่า default route ถ้า packet ตรงกับหลายกฎพร้อมกัน ระบบเลือกกฎที่เจาะจงที่สุด คือกฎที่ prefix ยาวที่สุด เรียกว่า longest prefix match เช่น packet ไป 10.0.3.42 ตรงทั้ง /16 และ /0 ระบบเลือก /16 packet จึงวิ่งภายใน VPC ไม่ออกไปข้างนอก เหมือนขับรถไปบางนาแล้วเจอป้าย "บางนา" กับป้าย "ทุกทิศทาง" ก็ต้องเลี้ยวตามป้ายบางนา

6. Internet Gateway และ NAT Gateway

Internet Gateway (IGW) คือประตูที่ให้ VPC คุยกับอินเทอร์เน็ตได้ทั้งขาเข้าและขาออก ผู้ให้บริการดูแลไม่ให้ล่มและขยายรับ traffic ได้เอง จึงไม่เป็น single point of failure (จุดเดียวที่ถ้าพังแล้วทั้งระบบพังตาม) VPC หนึ่งก้อนมี IGW ได้ตัวเดียว เครื่องที่มี public IP จะไม่เห็น public IP นั้นในตัวเอง เห็นแค่ private IP เพราะ IGW เป็นคนแปลงที่อยู่ให้แบบจับคู่หนึ่งต่อหนึ่ง เรียกว่า 1:1 NAT (Network Address Translation การแปลงที่อยู่ IP ที่เรียนในช่วงที่ 1)

ปัญหาคือเครื่องใน private subnet ก็ต้องออกเน็ตบ้าง เช่น โหลด patch (ตัวแก้ช่องโหว่) แต่ถ้าใส่เส้นทางไป IGW ก็จะกลายเป็น public ทันที ทางออกคือ NAT Gateway ซึ่งทำงานแบบ router ที่บ้านในช่วงที่ 1 ให้เครื่องข้างในออกไปได้ แต่คนข้างนอกเริ่มการเชื่อมต่อเข้ามาไม่ได้

จุดที่ตอบผิดบ่อยคือ ตัว NAT Gateway ต้องวางไว้ใน public subnet เพราะ NAT เองก็ต้องส่ง packet ต่อออกทาง IGW เส้นทางจริงจึงเป็น เครื่องใน private subnet → NAT Gateway (อยู่ใน public subnet) → IGW → อินเทอร์เน็ต และควรมี NAT หนึ่งตัวต่อ AZ เพื่อไม่ให้ AZ หนึ่งล่มแล้วพาทุก private subnet ออกเน็ตไม่ได้

วิธีพิสูจน์ว่า traffic ขาออกวิ่งทางไหนจริง คือถามเว็บภายนอกว่าเห็นเราเข้ามาจาก IP อะไร เครื่องใน public subnet จะได้ public IP ของตัวเอง ส่วนเครื่องใน private subnet จะได้ IP ของ NAT Gateway ซึ่งยืนยันว่าขาออกผ่าน NAT จริง

เมื่อต่อทุกอย่างเป็นเว็บหนึ่งเว็บ คำขอของผู้ใช้วิ่งจากอินเทอร์เน็ตเข้า IGW ไปที่ load balancer ใน public subnet ต่อไปที่ app server ใน private subnet แล้วถึงฐานข้อมูลใน private subnet อีกชั้น สองทอดหลัง คือจาก load balancer ไป app server และจาก app server ไปฐานข้อมูล ใช้กฎ local ส่วนเวลาที่ app server ต้องออกไปเรียกบริการภายนอกจะออกทาง NAT Gateway หลักคิดคือของที่สำคัญที่สุดต้องอยู่ลึกที่สุด ผู้โจมตีจะได้ต้องผ่านหลายด่าน

7. SDN: แยกงานคิดเส้นทางออกจากงานส่ง packet

router ส่ง packet ข้ามเครือข่าย ส่วน switch ส่ง packet ต่อกันภายในเครือข่ายเดียวกัน อุปกรณ์ทั้งสองแบบมีงานสองอย่าง งานแรกคือคิดว่า packet ควรไปทางไหน เรียกว่า control plane งานที่สองคือส่ง packet ออกไปตามเส้นทางที่คิดไว้แล้ว เรียกว่า data plane

งานคิดเส้นทางทำโดยแลกข้อมูลกับอุปกรณ์ตัวอื่นผ่าน routing protocol ซึ่งเป็นกติกาที่ router ใช้บอกกันว่าไปเครือข่ายไหนได้ทางไหน ตัวอย่างคือ OSPF ที่ใช้ภายในองค์กร และ BGP ที่ใช้ระหว่างองค์กรบนอินเทอร์เน็ต

เครือข่ายแบบเดิมรวมสองงานไว้ในกล่องเดียว จะเปลี่ยนการตั้งค่าก็ต้องเข้าไปสั่งทีละเครื่อง ถ้ามีอุปกรณ์สิบตัวยังพอไหว แต่ Cloud มีอุปกรณ์หลายพันตัว และลูกค้าก็สร้างเครือข่ายใหม่อยู่ตลอดเวลา จึงทำแบบนั้นไม่ได้

SDN (Software-Defined Networking) แยก control plane ออกจาก data plane แล้วรวมงานคิดไว้ที่โปรแกรมกลางชื่อ SDN controller ตัว controller มองเห็นทั้งเครือข่าย คำนวณเส้นทาง แล้วส่งกฎลงไปให้ switch ส่วน switch เหลืองานเดียวคือส่ง packet ตามกฎให้เร็วที่สุด ผลคือควบคุมทั้งเครือข่ายจากจุดเดียว และสั่งงานผ่าน API (Application Programming Interface ช่องทางที่โปรแกรมใช้สั่งงานโปรแกรมอื่น) จึงเขียนโปรแกรมให้ทำงานอัตโนมัติได้ และไม่ผูกกับผู้ผลิตรายใด VPC บน Cloud ก็ทำงานแบบนี้ เมื่อเรากดสร้าง route table คำสั่งจะไปที่ controller แล้วกระจายกฎลงไปที่ switch จริงหลายพันตัวให้เอง

ที่แยกแล้วดีขึ้นเพราะสองงานต้องการความเร็วต่างกันมาก งานคิดช้าได้เพราะเส้นทางไม่ได้เปลี่ยนบ่อย แต่งานส่งต้องจัดการ packet หลายล้านตัวต่อวินาทีจึงต้องใช้ฮาร์ดแวร์เฉพาะทาง เมื่อแยกกันแล้ว งานคิดย้ายไปรันบน server ธรรมดาได้ ส่วน switch ก็ทุ่มฮาร์ดแวร์ให้งานส่งอย่างเดียว controller สั่ง switch ผ่าน protocol มาตรฐานชื่อ OpenFlow switch เก็บคำสั่งไว้ใน flow table ซึ่งแต่ละแถวเป็นคู่ของเงื่อนไข (match) กับสิ่งที่ต้องทำ (action) เช่น ถ้าปลายทางอยู่ใน 10.0.3.0/24 (match) ให้ส่งออกทาง port 5 ของ switch (action) เพราะเป็นมาตรฐานกลาง จะใช้ switch ยี่ห้อไหนก็ได้

8. NFV: เปลี่ยนกล่องอุปกรณ์เครือข่ายให้เป็นโปรแกรม

อุปกรณ์อย่าง firewall, load balancer และ router แต่เดิมขายเป็นกล่องฮาร์ดแวร์เฉพาะทาง ราคาแพง และถ้ารับงานไม่ไหวก็ต้องรอซื้อกล่องใหม่ NFV (Network Functions Virtualization) เปลี่ยนงานของกล่องเหล่านั้นเป็นซอฟต์แวร์ที่รันเป็น VM หรือ container บน server ธรรมดา แนวคิดเดียวกับ virtualization ในช่วงที่ 1 แต่จำลองอุปกรณ์เครือข่ายแทนคอมพิวเตอร์ ข้อดีคือไม่ติดผู้ผลิตรายเดียว เปิดใช้ได้ในไม่กี่วินาที เพิ่มจำนวนตามงานได้ และถูกกว่า อีกข้อคือ service chaining ซึ่งให้ traffic ผ่านอุปกรณ์เสมือนหลายตัวต่อกันเป็นสาย เช่น firewall แล้วไป load balancer จะสลับลำดับก็แค่แก้การตั้งค่า ไม่ต้องย้ายสาย

SDNNFV
เปลี่ยนอะไรวิธีตัดสินว่า packet ไปทางไหนที่ที่งานของอุปกรณ์เครือข่ายรันอยู่ จากกล่องเป็นโปรแกรม
แนวคิดหลักแยก control plane ออกจาก data planeเปลี่ยนฮาร์ดแวร์เฉพาะทางให้เป็นซอฟต์แวร์
คำที่บอกใบ้ในโจทย์controller, OpenFlow, flow tableVM, service chaining, virtual firewall

SDN กับ NFV ไม่ได้แข่งกันแต่ใช้เสริมกัน SDN ตัดสินว่า traffic ไปทางไหน NFV ทำให้อุปกรณ์ที่ traffic ผ่านกลายเป็นโปรแกรม ข้อสอบชอบหลอกให้สลับสองคำนี้ และจำไว้ว่า OSPF กับ BGP เป็นงานฝั่ง control plane

9. สถาปัตยกรรมแบบ Tier

เว็บหนึ่งเว็บมีงานหลักสามส่วน คือหน้าเว็บที่ผู้ใช้เห็น โปรแกรมฝั่ง server ที่ประมวลผล และฐานข้อมูล Single-tier เอาทั้งหมดไว้เครื่องเดียว ถูกและง่าย แต่เป็น single point of failure และถ้าเว็บโดนเจาะ ผู้โจมตีได้ฐานข้อมูลไปด้วยทันที จึงเหมาะแค่การพัฒนาและทดสอบ Two-tier แยกฐานข้อมูลไปไว้ใน private subnet จึงปลอดภัยขึ้น แต่ส่วนหน้ายังอยู่เครื่องเดียว ไม่มี load balancer ล่มเมื่อไรเว็บก็ล่ม

Three-tier เป็นมาตรฐานของระบบจริง ชั้น presentation อยู่ใน public subnet มี load balancer กระจายงานให้ web server หลายเครื่อง ชั้น application ประมวลผลตามกฎธุรกิจ (business logic เช่น คิดราคา ตัดสต็อก) อยู่ใน private subnet ชั้น data คือฐานข้อมูล อยู่ใน private subnet และออกเน็ตไม่ได้ แต่ละชั้นคุยกับชั้นที่ติดกันเท่านั้น และมี SG ของตัวเอง (ช่วงที่ 3) ถ้าออกแบบดี ชั้นหนึ่งมีปัญหาก็จะไม่ลามไปถึงชั้นอื่น

ข้อดีอีกข้อคือแต่ละชั้นขยายแยกกันได้ สองชั้นแรกขยายแนวนอนได้ง่าย คือเพิ่มจำนวนเครื่อง ซึ่งมักใช้ Auto Scaling ที่เพิ่มลดจำนวนเครื่องให้เองตามปริมาณงาน ที่ทำได้ง่ายก็เพราะเครื่องในสองชั้นนี้ไม่เก็บข้อมูลไว้กับตัว (stateless) เครื่องใหม่ทำงานแทนกันได้ทันที ส่วนชั้น data ขยายยากกว่า เพราะการเขียนข้อมูลต้องรวมไว้ที่จุดเดียว ข้อมูลจึงจะไม่ขัดกัน จึงมักขยายแนวตั้ง (เปลี่ยนเป็นเครื่องใหญ่ขึ้น) หรือเพิ่ม read replica (สำเนาที่ช่วยรับงานอ่านแต่ไม่รับงานเขียน)

Multi-tier ใช้กับระบบใหญ่ โดยเพิ่มชั้นเข้ามาแก้ปัญหาเฉพาะเรื่อง เช่น CDN (Content Delivery Network) เก็บสำเนาไฟล์ไว้ใกล้ผู้ใช้เพื่อลดระยะทาง API Gateway เป็นด่านหน้าที่ตรวจตัวตนและจำกัดจำนวนคำขอ cache เก็บข้อมูลที่ถูกอ่านบ่อยไว้ในหน่วยความจำเพื่อลดภาระฐานข้อมูล และ message queue พักงานที่ไม่ต้องทำทันที เช่น ส่งอีเมลยืนยัน ผู้ใช้จะได้ไม่ต้องรอ หลักการเลือกคือเริ่มจากแบบง่ายก่อน แล้วค่อยเพิ่มชั้นเมื่อมีปัญหาที่ต้องแก้จริง

เทียบทั้งสี่แบบแล้ว ยิ่งเพิ่มชั้น ระบบยิ่งทนทานและขยายได้ดีขึ้น แต่ก็แพงและซับซ้อนขึ้นตาม ถ้าโจทย์ถามว่าควรเลือกแบบไหน ให้ดูว่างานใหญ่แค่ไหนและล่มได้หรือไม่

แบบจำนวนชั้นเหมาะกับจุดอ่อนหลัก
Single-tier1การพัฒนา ทดสอบ และโปรเจกต์ส่วนตัวพังพร้อมกันทั้งระบบ และเว็บโดนเจาะเท่ากับฐานข้อมูลโดนด้วย
Two-tier2แอปเล็ก MVP (แอปรุ่นแรกที่มีแค่ฟีเจอร์ที่จำเป็น) และเครื่องมือที่ใช้ภายในองค์กรส่วนหน้าเป็นเครื่องเดียว ไม่มี load balancer
Three-tier3เว็บแอปที่ใช้งานจริงทั่วไปซับซ้อนและแพงขึ้นในระดับปานกลาง
Multi-tier4 ขึ้นไประบบใหญ่ที่คนใช้มาก และแตกเป็น microservicesซับซ้อนและแพงที่สุด

10. Azure VNet ต่างจาก AWS VPC ตรงไหน

ข้อต่างที่สำคัญที่สุดคือการออกอินเทอร์เน็ต AWS เริ่มจากปิดแล้วให้เราเปิดเอง คือต้องสร้าง IGW และเพิ่ม route เอง ส่วน Azure เริ่มจากเปิดแล้วให้เราปิดเอง คือทุก subnet ออกอินเทอร์เน็ตได้เป็นค่าเริ่มต้น วิธีปิดคือสร้าง route table ของเราเอง ซึ่ง Azure เรียกว่า UDR (User Defined Route) ให้ 0.0.0.0/0 ชี้ไปที่ NAT Gateway แล้วผูกเข้ากับ private subnet เครื่องข้างในจึงออกเน็ตได้ขาเดียวเหมือนฝั่ง AWS ข้อต่างที่สองคือ subnet ของ AWS อยู่ใน AZ เดียว ถ้าจะกระจายข้าม AZ ต้องสร้างหลาย subnet แต่ subnet ของ Azure ครอบคลุมทั้ง Region ส่วนการเชื่อมสองเครือข่ายเข้าหากัน AWS เรียก VPC Peering และ Azure เรียก VNet Peering

11. แล็บ GetStart: Bastion และ Port mapping

แล็บนี้จำลองผู้ให้บริการ Cloud ขนาดเล็ก แต่ละกลุ่มได้ VPC ที่มี public subnet กับ private subnet เครื่องที่นักศึกษาสร้างอยู่ใน public subnet ก็จริง แต่มีแค่ private IP ข้อนี้ย้ำว่าอยู่ใน public subnet อย่างเดียวยังไม่พอ เครื่องต้องมี public IP ด้วยคนข้างนอกจึงจะเข้าถึงได้ ในแล็บนี้คนข้างนอกจึงเข้าได้แค่ผ่าน bastion หรือ port mapping ของเครื่องจริง (ดูด้านล่าง) ถ้า SSH (Secure Shell โปรแกรมรีโมตเข้าไปสั่งงานเครื่องอื่นแบบเข้ารหัส) จากโน้ตบุ๊กตรง ๆ จะไปไม่ถึง เพราะ router บนอินเทอร์เน็ตไม่ส่งต่อ packet ที่ไปหา private IP ต้อง SSH ไปที่ bastion (jump host) ก่อน แล้วจึงต่อเข้าเครื่องข้างใน (ตัวเลือก ProxyJump ของ ssh ทำสองต่อนี้ในคำสั่งเดียว)

ทำไมต้องผ่าน bastion นอกจากเครื่องข้างในไม่มี public IP จึงเข้าตรงไม่ได้อยู่แล้ว ต่อให้เข้าตรงได้ก็ไม่ควร เพราะถ้าทุกเครื่องเปิด SSH ให้คนทั้งโลก เราต้องเฝ้าประตูหลายสิบบาน bastion ทำให้เหลือประตูบานเดียวที่ป้องกันให้แน่นหนาและบันทึกได้ว่าใครเข้ามาเมื่อไร

เครื่องจริงของแล็บมี public IP ตัวเดียวที่ทุกกลุ่มใช้ร่วมกัน จึงต้องแยกแต่ละกลุ่มด้วยเลข port วิธีนี้เรียกว่า port mapping คือเครื่องจริงรับคำขอที่ port หนึ่ง แล้วส่งต่อไปให้ web server ของกลุ่มนั้นที่ port 80 ข้างใน (ในแล็บใช้ Nginx ซึ่งเป็นโปรแกรม web server ที่นิยมมาก) เหมือนเบอร์โทรหลักของบริษัทที่โอนสายต่อไปยังเบอร์ภายใน ถ้าไม่ได้ตั้ง port mapping ไว้ เว็บนั้นจะเปิดได้จากใน VPC เท่านั้น

12. แล็บ WebApp: แอปสามชั้น, REST API และ CORS

แล็บนี้ลงมือสร้างแอป three-tier ขนาดเล็กขึ้นมาจริง ชั้นแรกคือ web server ที่เก็บหน้าเว็บ ชั้นที่สองคือ API ที่ประมวลผล และชั้นที่สามคือฐานข้อมูล ฐานข้อมูลไม่เปิด port ให้ข้างนอกเลย และ API ต่อฐานข้อมูลด้วย private IP ภายใน VPC

API ใช้รูปแบบ REST (Representational State Transfer) ซึ่งใช้ path ใน URL (ส่วนที่ต่อท้ายชื่อเว็บ เช่น /api/products) บอกว่าพูดถึงข้อมูลอะไร และใช้ HTTP method บอกว่าจะทำอะไรกับข้อมูลนั้น GET คืออ่าน POST คือสร้างใหม่ PUT คือแก้ไข และ DELETE คือลบ เช่น GET /api/products คือขอรายการสินค้า server ตอบกลับเป็น JSON (JavaScript Object Notation รูปแบบข้อความสำหรับส่งข้อมูลระหว่างโปรแกรม)

API contract คือข้อตกลงที่ชัดเจนว่า API มีทางเข้า (endpoint) อะไรบ้าง แต่ละทางรับข้อมูลแบบไหนและตอบแบบไหน เหมือนเมนูอาหารที่ลูกค้าสั่งได้โดยไม่ต้องรู้ว่าในครัวทำยังไง ตราบใดที่สองฝั่งรักษาข้อตกลงนี้ไว้ frontend (ส่วนที่ผู้ใช้เห็น) กับ backend (ส่วนประมวลผลและเก็บข้อมูล) ก็เปลี่ยนภายในของตัวเองได้โดยไม่กระทบกัน และ API ชุดเดียวใช้ร่วมกันได้ทั้งแอปมือถือ เว็บ และแดชบอร์ด

ในแล็บ หน้าเว็บกับ API อยู่คนละ port browser จึงมองว่าทั้งสองมาจากคนละ origin คำว่า origin หมายถึงชุดของสามอย่าง คือ scheme (http หรือ https), host (ชื่อเครื่องหรือ IP) และ port ถ้าต่างกันแม้อย่างเดียวก็นับเป็นคนละ origin

browser มีกฎชื่อ same-origin policy ที่ไม่ยอมให้ JavaScript (ภาษาโปรแกรมที่รันอยู่ในหน้าเว็บ) อ่านข้อมูลที่ได้จาก origin อื่น เว้นแต่ server ปลายทางจะบอกว่าอนุญาต วิธีบอกคือใส่ header (ข้อมูลกำกับที่แนบมากับคำขอหรือคำตอบของ HTTP) ชื่อ Access-Control-Allow-Origin มาในคำตอบ กลไกนี้เรียกว่า CORS (Cross-Origin Resource Sharing)

กฎนี้มีไว้ปกป้องผู้ใช้ ไม่ได้ปกป้อง server สมมติเรา login เว็บธนาคารค้างไว้แล้วเผลอเปิดเว็บแปลก ๆ ถ้าไม่มีกฎนี้ JavaScript ของเว็บแปลก ๆ ก็ส่งคำขอไปธนาคารโดยอาศัยสถานะ login ของเรา แล้วอ่านข้อมูลบัญชีกลับไปได้ ข้อสอบชอบหลอกว่า CORS ป้องกัน API ซึ่งไม่จริง ใครก็ยังยิงคำขอเข้า API ด้วย curl (โปรแกรมบรรทัดคำสั่งสำหรับส่งคำขอ HTTP) ได้ตามปกติ เพราะคนที่บังคับใช้กฎคือ browser และ curl ไม่ใช่ browser

อีกข้อที่แล็บเน้นคือหน้าเว็บไม่ควรต่อฐานข้อมูลตรง ๆ เพราะต้องใส่รหัสผ่านฐานข้อมูลไว้ใน JavaScript ซึ่งใครเปิดหน้าเว็บก็กดดูได้ API จึงต้องเป็นด่านกลางเสมอ รหัสผ่านอยู่ที่ฝั่ง server ซึ่งผู้ใช้มองไม่เห็น

คำถามท้ายแล็บที่ควรตอบได้มีอีกสามข้อ ข้อแรก ถ้า API ล่มแต่ Nginx กับฐานข้อมูลยังทำงานอยู่ หน้าเว็บจะยังโหลดขึ้น เพราะ Nginx ส่งไฟล์หน้าเว็บได้ตามปกติ แต่จะไม่มีสินค้าแสดง เพราะ JavaScript ไปขอข้อมูลจาก API ไม่สำเร็จ นี่คือผลของการแยกชั้น ชั้นที่ล่มไม่ได้พาชั้นอื่นล่มตาม แต่ส่วนที่ต้องพึ่งชั้นนั้นจะใช้ไม่ได้ ข้อที่สอง บรรทัด CORS(app) ที่ไม่ได้ระบุอะไรเพิ่มจะอนุญาตทุก origin หน้าเว็บของกลุ่มอื่นจึงเรียก API ของเราแล้วอ่านผลได้ด้วย ถ้าอยากให้เฉพาะหน้าเว็บของเราอ่านได้ ต้องระบุ origin ที่อนุญาตให้ชัด

ข้อที่สาม มีอีกทางที่ไม่ต้องใช้ CORS เลย คือให้ Nginx รับคำขอที่ขึ้นต้นด้วย /api แล้วส่งต่อไปที่ API เอง ตัวกลางที่รับคำขอแทน server ข้างหลังแบบนี้เรียกว่า reverse proxy เมื่อหน้าเว็บกับ API มาจาก host และ port เดียวกัน browser ก็นับเป็น origin เดียวกัน จึงไม่ต้องมี header ของ CORS

13. แล็บ Build VPC: กั้น traffic ด้วย iptables

ในแล็บก่อน ๆ ทุกเครื่องใน VPC คุยกันได้หมด แม้แต่ bastion ก็ต่อตรงไปฐานข้อมูลได้ ซึ่งขัดกับหลัก three-tier แล็บนี้จึงให้แก้ด้วย iptables ซึ่งเป็น firewall ที่มากับ Linux ผังของแล็บมี bastion, app และ db อยู่ใน VPC เดียวกัน เป้าหมายเขียนเป็นตาราง connectivity matrix ที่บอกว่าเครื่องไหนต้องคุยกับเครื่องไหนได้หรือไม่ได้ ให้จำเหตุผลของแต่ละแถวมากกว่าตัวตาราง

ต้นทาง → ปลายทางผลที่ต้องได้เหตุผล
Bastion → App (เว็บ)ผ่านผู้ดูแลต้องตรวจได้ว่าเว็บทำงาน
Bastion → DBบล็อกbastion เสี่ยงโดนเจาะที่สุด ถ้าโดนแล้วต้องไปถึงข้อมูลตรง ๆ ไม่ได้
App → DBผ่านapp เป็นชั้นเดียวที่มีสิทธิ์อ่านเขียนข้อมูล

กฎของ iptables แบ่งกลุ่มตามทิศทางของ packet เรียกว่า chain คือ INPUT (packet ที่มาถึงเครื่องนี้), OUTPUT (packet ที่เครื่องนี้ส่งออก) และ FORWARD (packet ที่แค่ผ่านเครื่องนี้ไปที่อื่น) ระบบตรวจกฎจากบนลงล่าง กฎแรกที่ตรงเป็นตัวตัดสินว่าจะรับ (ACCEPT) หรือทิ้ง (DROP) ถ้าไม่ตรงกฎไหนเลยใช้ค่าเริ่มต้นของ chain นั้น ซึ่งเรียกว่า policy

หลักที่ใช้คือ default deny ปิดทุกอย่างไว้ก่อนแล้วเปิดเฉพาะที่จำเป็น เหตุผลคือ ถ้าลืมเปิดอะไรสักอย่าง ผลเสียมีแค่ใช้งานบางอย่างไม่ได้ ซึ่งรู้ตัวทันทีและแก้ได้ แต่ถ้าเริ่มจากเปิดหมดแล้วลืมปิดบางช่อง ช่องนั้นจะเป็นช่องโหว่ที่ไม่มีใครรู้จนกว่าจะโดนเจาะ

ในแล็บนี้ bastion ไม่ได้เป็นแค่ประตูให้คน SSH เข้ามา แต่ยังเปิด IP forwarding ให้ทำหน้าที่เป็น router ที่ส่ง packet ต่อระหว่างเครื่องด้วย packet ระหว่าง app กับ db จึงวิ่งผ่าน bastion และกฎที่คุมว่าใครคุยกับใครได้ก็เขียนไว้ใน chain FORWARD ของ bastion ส่วนค่าเริ่มต้นใช้ default deny กับขาเข้า คือตั้ง policy ของ INPUT กับ FORWARD เป็น DROP แต่ปล่อย OUTPUT เป็น ACCEPT เพราะของที่เครื่องส่งออกเองไม่ใช่สิ่งที่ต้องกัน ขาเข้าจึงต้องมีกฎเปิดให้ทีละอย่าง รวมถึงกฎเปิด loopback (lo) ซึ่งเป็นช่องที่โปรแกรมในเครื่องใช้คุยกับตัวเอง เช่น การเรียก localhost ไม่อย่างนั้นโปรแกรมในเครื่องเดียวกันจะคุยกันเองไม่ได้

กฎที่ขาดไม่ได้คือกฎที่รับ packet สถานะ ESTABLISHED,RELATED ถ้าไม่มี เมื่อเครื่องส่งคำขอออกไป คำขอออกได้ แต่คำตอบที่วิ่งกลับเข้ามาทาง INPUT ไม่ตรงกฎไหนเลยจึงโดนทิ้ง การเชื่อมต่อจึงค้าง กฎนี้แก้ได้เพราะ Linux จดจำการเชื่อมต่อทุกเส้นไว้ ESTABLISHED คือ packet ของการเชื่อมต่อที่มีอยู่แล้ว เช่น คำตอบของคำขอที่เราส่งออกไป RELATED คือ packet ที่เกี่ยวเนื่องกับการเชื่อมต่อเดิม เช่น ข้อความแจ้ง error firewall ที่จำการเชื่อมต่อได้แบบนี้เรียกว่า stateful ซึ่งเป็นพฤติกรรมเดียวกับ SG ในช่วงที่ 3

บนเครื่อง DB ตั้งกฎให้รับ port ของฐานข้อมูลเฉพาะจาก IP ของ app เมื่อมีด่านซ้อนกันทั้งบน bastion และบน DB ถ้าด่านหนึ่งตั้งพลาด อีกด่านยังกันไว้ได้ นี่คือ defense in depth ส่วนในฐานข้อมูลก็สร้าง user ให้ app ที่ login ได้เฉพาะจาก IP ของ app และมีสิทธิ์แค่อ่าน เพิ่ม แก้ และลบข้อมูลในตาราง ลบทั้งตารางหรือสร้าง user ใหม่ไม่ได้ นี่คือ least privilege ถ้า app โดนเจาะ ความเสียหายก็จำกัดอยู่แค่สิทธิ์เหล่านี้

ตอนทดสอบเส้นที่ถูกบล็อก คำสั่งจะค้างจนหมดเวลา ไม่ได้ถูกปฏิเสธทันที เพราะ DROP ทิ้ง packet เงียบ ๆ โดยไม่ตอบอะไร ถ้าใช้ REJECT ฝั่งที่ส่งมาจะได้ข้อความปฏิเสธทันที firewall ส่วนใหญ่เลือก DROP เพราะไม่บอกอะไรผู้โจมตีเลย แม้แต่ว่ามีเครื่องนี้อยู่จริงหรือไม่

ทวนก่อนสอบ

เรื่องตัวเลขใช้สูตรเดียว จำนวน IP = 2(32 − prefix) แล้วบน AWS หักอีก 5 ตัวในทุก subnet (ไม่ใช่ 2 ตัวแบบเครือข่ายทั่วไป) /28 จึงแจกเครื่องได้จริงแค่ 11 ตัว ส่วนช่วง private ที่ชอบหลอกคือ 172.16.0.0/12 ซึ่งครอบคลุมแค่ 172.16 ถึง 172.31

การไล่ packet ในห้องสอบให้ถามทีละด่าน ปลายทางอยู่ในช่วง IP ไหน แล้วเปิด route table ของ subnet ต้นทางดูว่ากฎที่ prefix ยาวที่สุดส่งไปที่ไหน local คือคุยกันภายใน IGW แปลว่า subnet นี้เป็น public ส่วน NAT แปลว่าออกได้อย่างเดียว โดยตัว NAT Gateway ต้องอยู่ใน public subnet และอย่าลืมว่า subnet เป็น public ได้เพราะ route table แต่เครื่องจะถูกเข้าถึงจากข้างนอกได้ก็ต่อเมื่อมี public IP ด้วย

เรื่องแนวคิด ข้อสอบชอบหลอกให้สลับ SDN กับ NFV จำไว้ว่า SDN แยก control plane ออกจาก data plane แล้วรวมงานคิดไว้ที่ controller (OSPF กับ BGP เป็นงานฝั่ง control plane) ส่วน NFV เปลี่ยนกล่องอุปกรณ์เครือข่ายเป็นโปรแกรม เรื่อง tier ยิ่งเพิ่มชั้นยิ่งทนทานแต่แพงและซับซ้อนขึ้น ชั้นที่เป็น stateless ขยายแนวนอนได้ง่าย ส่วนชั้นฐานข้อมูลมักขยายแนวตั้งหรือเพิ่ม read replica

จากแล็บ ให้จำว่า CORS ถูกบังคับใช้โดย browser จึงปกป้องผู้ใช้ แต่ไม่ได้กันใครยิง API ด้วย curl และ CORS(app) ที่ไม่ระบุ origin เปิดให้หน้าเว็บของใครก็อ่านผลได้ ส่วน iptables ตรวจกฎจากบนลงล่างและกฎแรกที่ตรงชนะ ถ้าขาดกฎ ESTABLISHED,RELATED คำตอบจะกลับเข้ามาไม่ได้ และ DROP ทำให้คำสั่งค้างจนหมดเวลา หลักวางของสำคัญไว้ลึกที่สุดกับ default deny จะต่อยอดเป็น SG, NACL และหลักการออกแบบในช่วงที่ 3
